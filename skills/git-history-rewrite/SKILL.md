# Git 历史改写

## 角色

你是本仓库的**历史改写工程师**。历史改写是**不可逆操作**（改写后需强推覆盖远程，影响所有 clone 者）：执行纪律是**先备份 → 先出方案 → 改写 → 四重验证 → 确认后强推**。全程在指定分支（默认 `main`）上操作，备份分支保留改写前状态供回退与对比。

## 适用与边界

**适用**（结构性修正既有提交）：

| 操作 | 说明 |
|---|---|
| 拆分提交 | 一次提交的改动按文件拆成多个提交（如把发版文件从功能提交中拆出） |
| 改类型/标题 | 提交信息不符合规范时 reword（如 `docs` 改 `chore(release)`、补 scope） |
| 重排顺序 | 提交在历史中的位置不对（如发版提交应位于版本最后一个功能提交之后） |
| 删除提交 | 移除不合规的提交（如发版后对已发布条目的补记） |
| 恢复时间 | rebase / filter 重写后 author / committer 时间变成重写当天，恢复为原提交时间 |

**不适用（改用其他技能）**：

- 把分支**回滚**到历史版本（reset / revert，不动既有提交结构）→ `git-rollback`；
- 清理已合并 / 过期分支 → `git-clean-branches`；管理 worktree → `git-worktree`；
- 只做代码评审、不改写 → `code-review`（改写前可用它核查现状提交）；
- 对未提交的工作区改动做拆分 / 整理 → 按 `commit-create` 提交时拆分。

## 要求

1. **先备份分支**：改写前 `git branch backup/<分支>-<日期>[-<主题>]`（如 `backup/main-20260915`、`backup/main-20260917-changelog-cn`），备份分支保持不动——它是回退依据与「树一致性」验证的对比基准。**同日第二次改写、或同一日改不同主题时给名字加主题后缀**：同名分支已存在会让 `git branch` 直接失败，而 `git branch -f` 会覆盖掉同名旧备份（旧备份可能仍是回退基准，不能用）。
2. **先取证、先出方案**：列出**每个目标提交**的处理方式（拆分 / 改类型 / 重排 / 删除 / 时间恢复）、涉及文件、tag 重映射表，先给用户确认再动手；方案含「预期最终树与备份一致（或仅预期差异）」。
3. **拆分提交的固定顺序**（易错，照抄）：
   1. **先取原提交信息落盘**（`git log -1 --format='%B' HEAD > msg.txt`）——**必须在 `git reset` 之前**，reset 后 HEAD 已是父提交、取到的是父的信息；
   2. `git reset --soft HEAD^`——该提交改动全部进入暂存区；
   3. `git restore --staged <不属于本提交的文件>`——**暂存区默认含全部改动，先移出本次不提交的**，否则会被第一个 commit 一起带走；
   4. `git commit -F msg.txt`（功能部分，用原信息）→ `git add <其余文件>` → `git commit -F <发版/第二份信息>`；
   5. `git rebase --continue`。
4. **时间语义**：rebase / filter-branch 重建的提交 committer date 默认变成重写当天——**必须恢复为原提交时间**（author / committer 都恢复；拆分一个提交产生的多个新提交沿用原提交时间）。恢复方法见「时间恢复」。
5. **发版提交规则**（改写涉及版本提交时逐项核对）：`chore(release): 发布 vX.Y.Z` 类型；只动版本文件；**位于该版本最后一个功能提交之后**；条目一次写全、**创建后不得被后续提交修改**（含补记）。
6. **四重验证**（全部通过才强推）：① 树一致性——`git diff backup/<分支>-<日期> <分支>` 为空或仅方案声明的差异；② 提交规则——版本文件归属、发版提交位置 / 条目不可变、`check-version.py` 通过；③ 时间语义——抽查 author / committer 为原时间；④ tag 指向——每个 tag 指向正确的发版/目标提交。
7. **强推前确认**：改写后本地历史与远程分叉，`--force-with-lease` 推分支、`--force` 推 tags 属覆盖远程的破坏性操作，须用户明确确认（含影响说明：协作者 clone 需重新同步）。
8. **失败可回退**：改写途中出错时，`git rebase --abort` 回到改写前（备份分支始终完好），或从备份分支重新开始；不硬撑。

## 执行步骤

### 第 1 步：备份与基线

```bash
git status --short                    # 工作区须干净
git branch backup/<分支>-<日期>        # 备份分支
git log --oneline --reverse <分支>     # 全量历史取证
```

### 第 2 步：取证制定方案

- 用 `git log --format` 定位目标提交：改过某文件的提交、某类型/标题的提交、tag 与提交的对应；
- 判断每类问题的归属：夹带版本文件（拆）、类型不符（改）、位置错误（重排）、发版后补记（删）、时间变当天（恢复）；
- 输出方案：`目标提交 → 处理方式 → tag 重映射`，交用户确认。

### 第 3 步：改写（rebase -i 非交互驱动）

- **标记 edit / reword**：`GIT_SEQUENCE_EDITOR="sed -i -e 's/^pick <hash>/edit <hash>/' ..." git rebase -i <起点>`；起点 = 第一个目标提交的父；
- **edit 点**：按「要求 3」拆分，或 `git commit --amend -F <新消息>` 改类型/标题；
- **重排**：todo 里把提交行移动到目标位置（如把发版提交行移到版本最后一个功能提交之后）；移动导致其后全部提交重放（committer 变当天，见第 4 步）；
- **删除**：todo 里删掉对应 `pick` 行；若删除提交的改动需并入其他提交，在 edit 点时手工合并后丢弃。
- **批量替换文件内容**（对既有多个提交做同一处文本替换，如小节标题统一）：用 `git filter-branch -f --index-filter '<替换脚本>' -- <分支>`，优先 `--index-filter`——它改索引里的 blob，不检出文件、绕开 `core.autocrlf` 的 CRLF 转换。替换模式**不带行尾锚定**（`s/^### Added/### 新增/` 而非 `s/^### Added$/…/`），改完**回读校验**：`git show <新提交>:<文件> | grep -c '<新内容>'`，条数须与方案一致。脚本可照抄 `references/index-filter.sh` 模板（改目标文件、命中模式、sed 规则三处）。

### 第 4 步：时间恢复（重写后必做）

rebase / filter-branch 后，重建提交的 committer 变重写当天。恢复：

1. **生成映射**：对每个提交，按「提交信息」在备份分支找原提交取 `%at %ct`；信息被改过的（改类型/拆分新建）用手动映射表（新提交 → 原提交，拆分的新提交沿用原提交时间）；
2. **filter-branch 应用**：
   ```bash
   git filter-branch -f --env-filter '
     rec=$(grep "^$GIT_COMMIT|" "<映射文件>" | head -1)
     if [ -n "$rec" ]; then
       at=$(echo "$rec" | cut -d"|" -f2); ct=$(echo "$rec" | cut -d"|" -f3)
       export GIT_AUTHOR_DATE="@$at"; export GIT_COMMITTER_DATE="@$ct"
     fi
   ' -- <分支>
   ```
   映射文件每行 `<完整hash>|<at>|<ct>`；
3. 拆分出的新提交时间可在 edit 点直接设置：`GIT_AUTHOR_DATE="@<epoch>" GIT_COMMITTER_DATE="@<epoch>" git commit --amend --reset-author --no-edit`。

### 第 5 步：重打 tag

```bash
git tag -d <tag>                       # 删旧 tag（指向改写前的提交）
git tag -a <tag> -m "<说明>" <新提交>   # 按方案的重映射打注解 tag
```

### 第 6 步：四重验证

1. **树一致性**：`git diff backup/<分支>-<日期> <分支> --stat`——空或仅方案声明的差异（如删除补记造成的 CHANGELOG 行）；
2. **提交规则**：改过 CHANGELOG / marketplace 的提交均为 `chore(release)` 或合法分发同步；发版提交位于版本最后、条目未被后续修改；`check-version.py` 通过；
3. **时间语义**：抽查拆分/改类型/重放提交的 `%ad %cd` 为原时间；
4. **tag 指向**：`git log -1 <tag>` 指向方案中声明的提交。

### 第 7 步：强推（用户确认后）

```bash
git push --force-with-lease origin <分支>
git push --force origin --tags
```

推后用 `check-version.py --remote` 核对远程一致。

## 验证

- 树一致性、提交规则、时间语义、tag 指向四重验证全部通过方可声明完成；任一项不通过先修复（从备份分支重做或定向修正），不静默放行。
- 强推后远程核对：`git ls-remote` / `check-version.py --remote`。

## 任务目标

按用户要求对既有提交做结构性修正（拆分 / 改类型 / 重排 / 删除 / 恢复时间），全程备份 + 方案先行 + 四重验证，确认后强推；失败可回退、不静默。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `TodoWrite` / `Task*` 工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **先取信息再 reset**：拆分提交时 `%B` 必须在 `git reset --soft` 之前落盘，否则取到父提交的信息（本次会话的真实教训）。
- **reset --soft 后先移出再提交**：暂存区含该提交全部改动，先 `git restore --staged` 移出不属于本次提交的文件，否则被第一个 commit 带走。
- **edit 标记可能不生效**：`GIT_SEQUENCE_EDITOR` 的 sed 按 hash 前缀匹配 todo 行，hash 缩写不匹配时会静默跳过——改写后核对每个目标是否真的被处理。
- **重排导致全链重放**：移动一个提交后，其后的提交全部重写（committer 变当天），时间恢复的映射要覆盖被重放的全部提交。
- **发版提交位置**：发版提交必须位于该版本最后一个功能提交之后；条目创建后不得修改，补充记入下一版本条目。
- **删除提交前确认内容**：确认被删提交的改动不承载仍需要的内容（并入其他提交或确实废弃）。
- **替换前先验行尾形态**：`--tree-filter` 检出的文件行尾由 `core.autocrlf` 决定（`true` 时为 CRLF），仓库对象里通常是 LF——依赖行尾的替换（多行字面量、`^…$` 锚定）会**静默失配**（脚本 exit 0、内容没换，曾因此把一次改写整个重做）。缺省用 `--index-filter` 改 blob 规避，改完一律回读校验条数。
- **替换脚本按字节改、不解码**：以二进制模式读写、按字面量换字节（不经解码/编码，不引入行尾转换，也不因文件含非 UTF-8 字节而崩）；替换词是纯文本时不要用正则（元字符会误伤）。全历史多分支批量替换则用 `--tree-filter` 调一个**独立幂等脚本**（对每个检出目录独立处理），跑前先在临时检出上验证替换条数。
- **备份分支别用 `-f` 覆盖**：同名备份已存在时 `git branch -f` 会把旧备份挪到新提交，丢掉原本的回退基准；改用带主题后缀的新名字。
- **强推影响面**：改写并强推后，所有 clone 的协作者历史分叉——先说明影响并获确认，不默认执行。
- **不做历史与对象清理**：`reflog expire` / `gc --prune=now` / `filter-repo` 默认不做（`filter-repo` 本机未安装时用 `filter-branch`，执行前说明其警告）。

## 输入

改写需求（可附带：目标提交或范围、期望的处理方式、是否已授权强推）：
