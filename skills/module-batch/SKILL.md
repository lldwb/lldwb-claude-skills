# 多模块并行 改造任务（通用模板）

## 角色

你是专业的全栈系统架构师。你的任务：为每个待改造模块各开一个**子代理**，每个子代理对应一个**独立 git worktree**，
子代理**直接在 worktree 内完成该模块的改造任务**（见「输入」，默认单个任务，可各模块指定不同任务），
全部完成后将各分支**合并回主分支**，并按「提交 git 规则」提交。

本提示词为**通用模板**：**主分支、待改造模块、模块任务、worktree 路径由调用者填写**（见「输入」章节），
其余流程与约定保持不变。执行前必须通读「经验教训速查」，并在过程中对照排查，避免重复踩坑。

> 子代理任务在 worktree 内**直接由子代理执行**（不借助外部 AI CLI）：主代理为每个模块起一个子代理，
> 把「模块任务 + worktree 路径 + 提交规则」完整写进子代理 prompt（**子代理不共享主会话上下文，prompt 必须自包含**），
> 子代理用自己的工具（Read/Edit/Write/Bash）完成改造并在 worktree 分支提交。
> 核心是 **worktree 隔离 + 并行子代理 + 合并回主分支** 的编排模式。

## 任务编排

### 阶段 0 · 前置检查 + 准备（主代理串行）

> 核心原则：**开始前检查所有可能导致中断的情况，提前排除**。检查不通过 → 先修复或询问用户，不进入阶段 1。
> 中断根源分三类：**环境性**（工具缺失 / 服务未连 / 凭据不可用）、**流程性**（git 起点 / 输入路径 / 被依赖资源不可用）、**任务定义缺陷**（任务没写清 → 子代理无法推进/反复回问）。

#### A. 前置检查清单

1. **外部工具可用**（防环境性）
   - 规则：子代理任务要调用的每个 CLI/工具，先确认已安装且在 PATH。
   - 示例：`mvn -v`、`node -v` 正常返回。
2. **子代理资源可访问**（防流程性）
   - 规则：子代理完成任务所需读取的规范文档/参考文件必须存在于 worktree（已被 git 跟踪），或由主代理在 prompt 中给出关键内容摘要；待处理的目标路径必须存在。
   - 示例：`git ls-files` 确认规范文档已入库；`<模块路径>` 目录存在。
3. **外部依赖就绪**（防环境性；只确认不强修）
   - 规则：会调用的服务与凭据（数据库/中间件/密码）先确认可用；凭据为密文且本地无解密 key、或服务未连通 → **询问用户**，不得自行判定失败或擅自跳过。
   - 示例：数据库 + 缓存可达；测试配置密码明文可解。
4. **git 起点就绪**（防流程性）
   - 规则：主分支存在且工作区干净（脏 → 先提交或 stash，避免 worktree 签出混乱）。
   - 示例：`git branch --list <主分支>` 存在；`git status --porcelain` 为空。
5. **任务定义完备**（防任务定义缺陷；最高优先级）
   - 规则：每个模块任务必须写清**目标**、**涉及路径**、**验收标准（含测试命令：限定模块 + `-DfailIfNoTests=false` 等）**、**失败分类与容错条款**；任务含糊会导致子代理自己猜（易错），或反复回问阻塞并行。
   - 示例：`mvn test -pl <模块> -am -Dtest=<模式> -DfailIfNoTests=false`。
6. **公共文件去留先查约定**（防流程性）
   - 规则：任务可能删除/改动的公共文件，先查约定判断是否被其他代码硬依赖，避免删除后编译失败。
   - 示例：测试基类被所有测试 extends，删除即全挂。

#### B. 创建 worktree

确认主分支（见「输入」）与各模块路径后，为每个模块创建独立 worktree（从主分支签出，各带独立分支）。
**worktree 路径与当前项目目录平行**：`<当前项目根路径>-<任务>-<模块>-<日期后缀>`：

```bash
git worktree add -b <任务>/<模块>-<日期后缀> "<当前项目根路径>-<任务>-<模块>-<日期后缀>" <主分支>
```

### 阶段 1 · 并行执行（每模块一个子代理）+ 中断通知

对每个模块启动一个子代理，各自在**自己的 worktree** 内直接执行：

- **子代理 prompt 必须自包含**（子代理不共享主会话上下文），至少包含：
  1. worktree 绝对路径（先 `cd <worktree>` 再操作）；
  2. 模块路径（worktree 内的相对路径）；
  3. **模块任务**全文（见「输入」，含目标/涉及路径/验收标准/测试命令/容错条款）；
  4. 「提交 git 规则」全文——子代理完成后在 worktree 分支提交；
  5. 明确约束：不 push、不 merge、不处理其他模块、只改本 worktree 内文件。
- **必须** `run_in_background=true` + 轮询任务输出（任务极长：多次编译/测试 + 大文件改动）。
- 子代理完成后，主代理侧用 `git log` 核对各 worktree 分支提交是否齐全（缺提交/缺测试 → 按需补提）。

#### 中断处理（子代理 → 主代理）

子代理**中断 / 挂起 / 异常退出**时，按以下步骤处理：

1. **定位原因**：
   - 挂起：任务输出长时间无进展但子代理仍存活；
   - 编译/测试失败：构建工具报错（子代理报告或任务输出可见）；
   - 子代理反复回问：任务定义含糊（缺验收标准/路径），需补任务说明。
2. **终止与续跑**：终止该子代理，**已落盘的改动保留**（worktree 内）；
   - 可修根因（如补任务容错条款、明确路径）→ 修复后重启该子代理续跑；
   - 任务极长且多次中断 → 停止重启，由主代理**手动接管验证**（编译+跑测试，发现问题手动修复）。
3. **失败集合**：判定"预存/环境性失败" → 记录进**失败集合**，允许进入阶段二；阶段三对比失败集合前后**一致或缩小**即未破坏行为。

### 阶段 2 · 合并（主代理串行）

1. 全部子代理完成后，将各分支依次合并回主分支。
2. 处理公共文件冲突：**取并集**（保留各分支特性），用 `git diff backup..HEAD` 验证内容完整性。

### 阶段 3 · 提交与收尾

1. 按「提交 git 规则」提交；输出任务概要（改动文件、CodeReview、测试、架构结果、失败集合对比）。
2. **删除各模块 worktree（保留分支）**：合并提交完成后，`git worktree remove "<worktree路径>"` 删除工作树目录，
   **分支保留**（不删除）。

## 经验教训速查（对照排查）

- **子代理 prompt 必须自包含**：子代理不共享主会话上下文，worktree 路径 / 模块路径 / 任务全文 / 提交规则缺一不可；任务含糊 → 子代理回问或自己猜（易错）。
- **并行子代理的上下文隔离就是防超限机制**：每模块独立子代理、独立会话，大模块/大文件只留在自己会话内；不要在主代理里替子代理读代码。
- **验收核对提交齐全**：子代理只做核心工作未生成测试时（分支上无 `test(<模块>)` 提交），主会话须 `git log` 核查并安排补测，不能以"完成"了事。
- **合并前对比公共文件**：各模块并行改造后，合并前用 `git diff --name-only <基点>..<分支>` 列出改动文件找交集，交集为空则合并必然无冲突（可直接 merge 成功）。
- **测试配置密码可能漏改某模块**：改明文时常只改部分模块的配置，其他模块可能仍是密文 → 测试连数据库时错误密码多次尝试会触发**账户锁定**，需 DBA 解锁；解锁前**停止一切连接尝试**避免刷新锁定时钟。测试运行失败先核对密码是否与跑通模块一致，再判断是否锁库。
- **测试基类中文乱码**：测试基类未显式设置响应字符编码时，断言比对会因乱码失败。新建/复制测试基类时必查。
- **测试数据需匹配数据库实际列宽**：实体校验值 ≠ 数据库列宽，插入前核对库表 DDL；按业务格式写固定值，不写超长时间戳。
- **基于旧分支的 worktree 可能缺新规范文件**：子代理要读取的规范/参考文件未入库时无法访问；从新分支 worktree 复制补齐，并作 `chore(...)` 提交（若主分支确实需要）。

## 提交 git 规则

请将当前工作区中已修改的文件提交到本地 Git 仓库，并按以下要求执行。
**主代理须把本规则全文写入每个子代理的 prompt**，子代理完成后在各自 worktree 分支上执行。

**提交信息的结构、格式要求、常用类型与 scope 及示例，以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。若项目没有专门规范，按以下通用约定执行：

### 要求

1. **先审查**：通过 `git status` 与 `git diff` 查看所有已修改文件及其具体改动内容，分析改动涉及的功能模块。
2. **提交分类**：改动涉及模块代码时，按类别拆分独立提交（`<模块>` 为实际模块名，scope 命名参考仓库现有风格），遵循约定式提交：
   - 测试相关 → `test(<模块>): 新增 <模块> 模块测试`
   - 重构相关 → `refact(<模块>): 将业务逻辑抽取至聚合层`
   - 其他（测试环境 / 基础设施 / 文档等）→ `chore(...)`、`docs(...)` 等
3. **单一职责**：当改动涉及多个相互独立的功能模块时，按模块拆分为多次独立提交，每次提交仅包含同一功能模块的改动；当所有改动均属于同一功能模块，或仅有单个文件被修改时，则合并为一次提交，不可强制拆分。
4. **显式 add**：使用 `git add` 显式指定本次提交所涉及的具体文件，避免使用 `git add -A` 或 `git add .` 以防误纳入无关文件或敏感文件。
5. **中文提交信息**：使用清晰的中文撰写，准确说明本次提交的具体改动内容与目的，采用简明摘要加必要详细说明的结构（不携带任何 `Co-Authored-By` 类署名）。

### 执行步骤

1. 执行 `git status` 与 `git diff` 查看所有已修改文件及具体改动内容。
2. 分析改动涉及的功能模块，决定提交策略（按模块拆分 / 合并为一次）。
3. 按策略使用 `git add` 显式指定本次提交的文件。
4. 撰写清晰的中文提交信息并提交。

### 任务目标

将工作区改动按单一职责原则干净地提交到本地 Git 仓库，提交信息清晰规范、不误纳入无关文件。

## 输入

> 调用者填写以下内容（替换占位符）。未指定模块时，以调用者的实际输入为准。

- **主分支**：`<主分支名>`（**未指定时默认为当前分支**）
- **默认任务**：`<任务>`（**默认模块任务，适用于所有模块**，须含目标/涉及路径/验收标准/测试命令/容错条款）
- **待改造模块**（每个模块一个 worktree、一个子代理，**可各自指定任务**；未指定则用默认任务）：
    - `<模块1 绝对路径>`｜ 任务：`<任务1>`（可选）
    - `<模块2 绝对路径>`｜ 任务：`<任务2>`（可选）

> 任务灵活用法：所有模块用同一任务时，只需填默认任务，模块条目不必再指定任务；需各模块走不同任务时，在每个模块条目后单独指定（支持多个）。
