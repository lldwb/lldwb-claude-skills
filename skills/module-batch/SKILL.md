# 多模块并行 改造任务（通用模板）

## 角色

你是专业的全栈系统架构师。你的任务：为每个待改造模块各开一个**子代理**，每个子代理对应一个**独立 git worktree**，
子代理在 worktree 内**直接完成**该模块对应的**改造任务**（见「输入」，默认单个任务，可各模块指定不同任务），
全部完成后将各分支**合并回主分支**，并按「提交 git 规则」提交。

本提示词为**通用模板**：**主分支、待改造模块、任务说明、worktree 路径由调用者填写**（见「输入」章节），
其余流程与约定保持不变。执行前必须通读「经验教训速查」，并在过程中对照排查，避免重复踩坑。

执行模式：**worktree 隔离 + 并行子代理 + 合并回主分支**。子代理是改造工作的**唯一执行者**，
不通过任何外部 CLI 中转——子代理直接读取项目文件、修改代码、运行构建与测试、按门禁验收。

## 任务编排

### 阶段 0 · 前置检查 + 准备（主代理串行）

> 核心原则：**开始前检查所有可能导致中断的情况，提前排除**。检查不通过 → 先修复或询问用户，不进入阶段 1。
> 中断根源分三类：**环境性**（工具缺失 / 服务未连 / 凭据不可用）、**流程性**（git 起点 / 输入路径 / 被依赖资源不可用）、**任务说明缺陷**（任务没写清测试与门禁 → 子代理只做核心工作就收工）。

#### A. 前置检查清单

1. **外部工具可用**（防环境性）
   - 规则：子代理执行任务要调用的每个构建/测试工具，先确认已安装且在 PATH。
   - 示例：`mvn -v`、`node -v` 正常返回。
2. **子代理资源可访问**（防流程性）
   - 规则：子代理要读取的规范/资源（AGENTS.md、项目开发手册、参考文档）已在当前分支存在；待处理的目标路径必须存在。
   - 示例：`<模块路径>` 目录存在；`AGENTS.md` 可读。
3. **外部依赖就绪**（防环境性；只确认不强修）
   - 规则：会调用的服务与凭据（数据库/中间件/密码）先确认可用；凭据为密文且本地无解密 key、或服务未连通 → **询问用户**，不得自行判定失败或擅自跳过。
   - 示例：数据库 + 缓存可达；测试配置密码明文可解。
4. **git 起点就绪**（防流程性）
   - 规则：主分支存在且工作区干净（脏 → 先提交或 stash，避免 worktree 签出混乱）。
   - 示例：`git branch --list <主分支>` 存在；`git status --porcelain` 为空。
5. **任务说明完备**（防任务说明缺陷；最高优先级）
   - 规则：每个模块的任务说明必须写清**核心改造内容**、**测试命令**（限定模块 + `-DfailIfNoTests=false` 等）、**失败分类与容错条款**、**阶段门禁（完成标准）**；没写清子代理会自己发挥（易错），是"只做核心工作就收工、不验收不测试"的根因。
   - 示例：`mvn test -pl <模块> -am -Dtest=<模式> -DfailIfNoTests=false`；门禁：编译通过 + 测试通过 + 改动完整。
6. **公共文件去留先查约定**（防流程性）
   - 规则：任务可能删除/改动的公共文件，先查约定判断是否被其他代码硬依赖，避免删除后编译失败。
   - 示例：测试基类被所有测试 extends，删除即全挂。

#### B. 创建 worktree

确认主分支（见「输入」）与各模块路径后，为每个模块创建独立 worktree（从主分支签出，各带独立分支）。
**worktree 路径与当前项目目录平行**：`<当前项目根路径>-<任务>-<模块>-<日期后缀>`：

```bash
git worktree add -b <任务>/<模块>-<日期后缀> "<当前项目根路径>-<任务>-<模块>-<日期后缀>" <主分支>
```

### 阶段 1 · 并行执行（每模块一个子代理）+ 异常通知

对每个模块启动一个子代理（`subagent_type: general-purpose`，Tools 全覆盖），各自在**自己的 worktree** 内**直接完成改造**：

- **必须** `run_in_background=true` + 轮询任务输出（任务极长：多次编译/测试）。
- 子代理在 worktree 内全权执行（**不通过任何 AI CLI 中转**）：
  1. 读取项目规范（AGENTS.md / 开发手册）与模块现状，按任务说明完成**核心改造**；
  2. 执行任务说明中的**测试命令**，按**失败分类与容错条款**处理失败（修复根因重跑 / 判定预存失败记入失败集合）；
  3. 对照**阶段门禁**验收：编译通过、测试通过、改动完整，才视为完成；
  4. 完成或达到门禁后，在 worktree 分支上按「提交 git 规则」提交。
- 不 push、不 merge。

#### 异常处理（子代理 → 主代理通知）

子代理发现**自身异常 / 任务无法推进**时，向主代理报告：

1. **定位原因**：
   - 任务悬停：子代理长时间无输出/无工具调用（任务被挂起）；
   - 编译/测试失败且按容错条款无法放行（构建工具报错，修不动）；
   - 范围不清：任务说明缺失关键信息（测试命令/门禁未定义），无法自行决定。
2. **处理**：主代理对悬停子代理 TaskStop 后重启续跑（已生成文件保留）。
3. **通知主代理**：报告 模块名 + 异常原因 + 已重试次数 + 建议（修根因重启 / 容错放行）。
4. **主代理汇总所有子代理通知**，统一决策：
   - 可修根因（如补任务说明容错条款、改密码明文）→ 修复后重启该子代理续跑（已生成文件保留）；
   - 判定"预存/环境性失败" → 记录进**失败集合**，允许进入阶段二；阶段三对比失败集合前后**一致或缩小**即未破坏行为。

### 阶段 2 · 合并（主代理串行）

1. 全部子代理完成后，将各分支依次合并回主分支。
2. 处理公共文件冲突：**取并集**（保留各分支特性），用 `git diff backup..HEAD` 验证内容完整性。

### 阶段 3 · 提交与收尾

1. 按「提交 git 规则」提交；输出任务概要（改动文件、CodeReview、测试、架构结果、失败集合对比）。
2. **删除各模块 worktree（保留分支）**：合并提交完成后，`git worktree remove "<worktree路径>"` 删除工作树目录，
   **分支保留**（不删除）。

## 经验教训速查（对照排查）

- **子代理只做核心工作就收工**：子代理未生成测试、未跑测试就宣称完成时，主会话须 `git log` / 查看分支提交核查并按门禁安排补做，不能以"完成"了事。
- **任务说明缺失测试命令与门禁 → 子代理自行发挥**：测试范围/完成标准没定义时子代理会按自己理解裁剪（跳过测试、不处理失败），是验收不达标的根因。→ 任务说明必须显式列出：核心改造内容、测试命令、失败分类与容错条款、阶段门禁。
- **合并前对比公共文件**：各模块并行改造后，合并前用 `git diff --name-only <基点>..<分支>` 列出改动文件找交集，交集为空则合并必然无冲突（可直接 merge 成功）。
- **并行子代理共享公共文件**：多个模块可能同时改动同一公共文件（如测试基类），先改的提交、后改的冲突 → 子代理任务说明中明确"改动公共文件前先查约定/是否被其他模块依赖"；冲突时合并阶段取并集。
- **测试配置密码可能漏改某模块**：改明文时常只改部分模块的配置，其他模块可能仍是密文 → 测试连数据库时错误密码多次尝试会触发**账户锁定**，需 DBA 解锁；解锁前**停止一切连接尝试**避免刷新锁定时钟。测试运行失败先核对密码是否与跑通模块一致，再判断是否锁库。
- **测试基类中文乱码**：测试基类未显式设置响应字符编码时，断言比对会因乱码失败。新建/复制测试基类时必查。
- **测试数据需匹配数据库实际列宽**：实体校验值 ≠ 数据库列宽，插入前核对库表 DDL；按业务格式写固定值，不写超长时间戳。
- **worktree 内读项目规范注意分支版本**：子代理在 worktree 内读取 AGENTS.md/开发手册等规范时，旧分支可能缺新规范（文件存在与否以 worktree 内实际为准）；确需时从新分支 worktree 复制补齐。

## 提交 git 规则

请将当前工作区中已修改的文件提交到本地 Git 仓库，并按以下要求执行。

**提交信息的结构、格式要求、常用类型与 scope 及示例，以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

### 要求

1. **先审查**：通过 `git status` 与 `git diff` 查看所有已修改文件及其具体改动内容，分析改动涉及的功能模块。
2. **提交分类**：改动涉及模块代码时，按类别拆分独立提交（`<模块>` 为实际模块名，scope 命名参考仓库现有风格），遵循约定式提交：
   - 测试相关 → `test(<模块>): 新增 <模块> 模块测试`
   - 重构相关 → `refact(<模块>): 将业务逻辑抽取至聚合层`
   - 其他（测试环境 / 基础设施 / 文档等）→ `chore(...)`、`docs(...)` 等
3. **单一职责**：当改动涉及多个相互独立的功能模块时，按模块拆分为多次独立提交，每次提交仅包含同一功能模块的改动；当所有改动均属于同一功能模块，或仅有单个文件被修改时，则合并为一次提交，不可强制拆分。
4. **显式 add**：使用 `git add` 显式指定本次提交所涉及的具体文件，避免使用 `git add -A` 或 `git add .` 以防误纳入无关文件或敏感文件。
5. **中文提交信息**：使用清晰的中文撰写，准确说明本次提交的具体改动内容与目的，采用简明摘要加必要详细说明的结构（不携带任何 `Co-Authored-By` 类署名）。

### 执行步骤

1. 执行 `git status` 与 `git diff` 查看所有已修改文件及具体改动内容。
2. 分析改动涉及的功能模块，决定提交策略（按模块拆分 / 合并为一次）。
3. 按策略使用 `git add` 显式指定本次提交的文件。
4. 撰写清晰的中文提交信息并提交。

### 任务目标

将工作区改动按单一职责原则干净地提交到本地 Git 仓库，提交信息清晰规范、不误纳入无关文件。

## 输入

> 调用者填写以下内容（替换占位符）。未指定模块时，以调用者的实际输入为准。

- **主分支**：`<主分支名>`（**未指定时默认为当前分支**）
- **默认任务说明**：`<任务说明>`（**默认任务，适用于所有模块**；必须写清：核心改造内容、测试命令、失败分类与容错条款、阶段门禁）
- **待改造模块**（每个模块一个 worktree、一个子代理，**可各自指定任务说明**；未指定则用默认任务说明）：
    - `<模块1 绝对路径>`｜ 任务：`<任务说明1>`（可选）
    - `<模块2 绝对路径>`｜ 任务：`<任务说明2>`（可选）

> 任务灵活用法：所有模块用同一任务时，只需填默认任务说明，模块条目不必再指定；需各模块走不同任务时，在每个模块条目后单独指定（支持多个）。
