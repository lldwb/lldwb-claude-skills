# 提交 git 改动

## 角色

你是本仓库的 **commit 专员**：只负责把工作区改动**干净、可读地**提交到本地仓库——审查改动、按单一职责组织提交、写清楚的中文提交信息。不替用户决定要不要改代码，也不自动 push。

**本技能是提交环节的唯一实现（SSOT 源）**：提交的完整细则（拆分判定、提交信息结构、暂存复核、提交前后自检）只在**本技能**维护；其他技能一律只保留最短的提交规则并指向本技能，不在别处重复展开，以避免同一套规则多处漂移。

## 适用与边界

**适用**：把当前工作区已修改 / 新增 / 删除的文件组织成一次或多次本地提交——先审查改动、按单一职责拆分、显式暂存、撰写中文提交信息、提交前后自检与复核。

**不适用（改用其他技能）**：

- 改动还没做完、需要先写或改代码 → 对应的开发技能（如 `bug-fix` / `feature-dev`）；本技能不替用户改代码。
- 用户要求建 MR / PR（合并请求）→ `mr-create`；本技能只在本地提交，不 push、不建合并请求。
- 需要评审某个已有提交 / 分支的质量 → `code-review`；本技能只负责"提交"，不下质量结论。

**范围外（不属于技能切换）**：清理历史与对象（`reflog expire` / `gc --prune=now` / `filter-repo` / 交互式 rebase）默认不做，确需时按「注意事项」的处置规则执行。

## 要求

1. **提交前先校验仓库状态**：`git rev-parse --is-inside-work-tree` 确认处于 Git 仓库；再检测三种「不该直接提交」的状态——rebase 中途（`.git/rebase-merge` / `.git/rebase-apply` 存在）、merge 冲突未解决（`.git/MERGE_HEAD` 存在）、detached HEAD（`git symbolic-ref -q HEAD` 无输出）。**命中任一状态时先报告并询问，不盲目提交**：rebase / merge 中途提示先处理完冲突或 `git rebase --abort`；detached HEAD 提示当前提交不属于任何分支，确认是否先切分支。
2. **先审查**：`git status` 与 `git diff` 查看所有已修改/新增/删除文件及具体改动内容，分析改动涉及的功能模块与变更主题。
3. **单一职责**：改动涉及多个相互独立的功能模块时，按模块拆分为多次独立提交，每次提交只包含同一功能模块的改动；所有改动属于同一模块、或仅单个文件被修改时，合并为一次提交，**不可强制拆分**。
4. **显式 add**：用 `git add <file>` 显式指定本次提交涉及的具体文件，**禁止** `git add -A` / `git add .`，防止误纳入无关文件、本地产物或敏感文件。
5. **中文提交信息**：用清晰的中文撰写，准确说明改动内容与目的，采用"简明标题 + 必要正文"的结构，并遵循仓库现有提交信息风格（见「提交信息结构」）。
6. **不越界**：不自动 push / merge / 建 PR（用户要求建 MR/PR 时转 `mr-create` 技能），不 `--force`，不改写已推送的历史。

## 执行步骤

1. **先校验仓库状态**（见「要求」第 1 条）：非 Git 仓库、rebase / merge 中途、detached HEAD 时先报告并询问，不进入后续步骤。
2. `git status` 看全貌（已修改、未跟踪、已暂存），`git diff` 看未暂存改动，必要时 `git diff <file>` 逐文件看。
3. 归纳改动：把每个文件归到功能模块 / 变更主题下，列出「提交批次 → 文件清单 → 一句话说明」。
4. 定提交策略（见「拆分判定」）；**默认直接提交并在汇报中列出 sha、文件清单与提交信息**，遇到需要确认的情形（含删除、重命名、生成物、拆分方案不唯一）先给用户方案；技能另有明确要求时从其规定（如 `repo-init` 的"提交前先问"）。
5. 按批次执行：`git add <file>`（显式列出）→ `git diff --staged` 复核暂存内容是否只含预期改动。
6. 撰写中文提交信息并提交（多行信息走消息文件，见「提交信息结构」）。
7. 按「验证」核验提交结果；信息被并入标题时按「验证」的处置方式修正（限未推送的本地分支）。
8. 汇报：每次提交的 sha、标题、文件清单；若有未提交的剩余改动，说明原因（如属于其他批次、疑似敏感、用户未授权）。

## 验证

提交后用 git 命令逐条核验，判定口径如下：

- `git log -1 --format='%s'` 应只有标题、`git log -1 --format='%b'` 应含完整正文；信息被并入标题时用 `git commit --amend -F <消息文件>` 修正（**限未推送的本地分支**，已推送的历史不改写）。
- `git show --stat <sha>` 的文件清单与本次预期批次逐项一致；混入本批次之外的文件时先撤出暂存再重提，不带进提交。
- `git status` 中的剩余改动与「未提交原因」的说明一致（属于其他批次 / 疑似敏感 / 用户未授权）。
- 抽查提交内容不含敏感信息（凭据 / token / 内网地址 / 真实数据样例 / 本机绝对路径），也不含本地产物（`.tasks/`、`__pycache__/`、`*.pyc`、构建产物、本地配置文件）。

**判定口径**：四项均通过（提交信息标题与正文已分离、文件清单与批次一致、剩余改动有说明、无敏感信息与本地产物）方可声明提交完成并继续下一批次；任一不通过时停下来修正或向用户报告，**不静默放行**。

## 任务目标

把当前工作区改动按单一职责组织成一次或多次**只落在本地**的提交：每次提交的文件清单与变更主题一致、提交信息为准确的中文且标题与正文已分离、提交内容不含本地产物与敏感信息；收尾汇报中交代每次提交的 sha、文件清单，以及未提交剩余改动的原因。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `TodoWrite` / `Task*` 工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **提交前自检**：
  - 是否有本地产物混入（`.tasks/`、`__pycache__/`、`*.pyc`、构建产物、本地配置文件）；确认 `.gitignore` 已覆盖，必要时先补 `.gitignore` 再提交。
  - 是否含敏感信息：凭据 / token / IP / 内网地址 / 真实数据样例 / 本地绝对路径 / 机器名与用户名；**发现即停止并报告**，不带入提交。
  - 是否漏了未跟踪的新文件（新建但未 add 的源码、配置模板）——`git status` 的 untracked 段逐个确认。
- **不要顺手改代码**：提交过程中发现代码问题，报告给用户，不擅自修改后再提交。
- **钩子失败不绕过**：pre-commit 等钩子报错时修问题本身，不用 `--no-verify` 跳过。
- **提交信息不照抄**：参考风格可以，具体文案按本次改动实际生成，不套用模板里的项目名或示例内容。
- **历史与对象清理是独立的重操作**：`--amend`（限未推送的本地分支）之外的手段——`reflog expire`、`gc --prune=now`、`filter-repo`、交互式 rebase——**默认不做**；确需清理历史时先说明不可逆后果并取得明确同意，事后用 `git fsck` 核验仓库完整性。
- **确认请求无应答时**：可逆改动按推荐方案继续，并在汇报首段标注"该决策未获用户确认"；含删除、历史改写、依赖或接口变更等不可逆、影响面大的改动，停下等待确认，不默认执行。

## 拆分判定

| 情形 | 处置 |
|---|---|
| 多个相互独立的模块/功能改动 | 拆分为多次提交，每次一个模块 |
| 同一模块内的多处改动 | 合并为一次提交 |
| 仅单个文件被修改 | 一次提交，不强制拆分 |
| 仓库尚无任何提交（首次提交） | 按最终工作区状态一次性提交，不制造中间态；纯格式化改动并入初始提交并在正文说明 |
| 业务改动与其配套的文档/测试（同一变更主题） | 合并为一次提交 |
| 独立发起的文档更新（与本次业务改动无关） | 单独 `docs(...)` 提交 |
| 纯格式化/重命名 与 业务改动混在一起 | 分开提交（先格式化/重命名，再业务改动），便于评审 |
| 单次 diff 规模大（如 > 300 行）或跨多个顶级目录 | 先给拆分方案（按关注点 / 文件模式分组，并给出各组的 pathspec），确认后按组提交 |
| 含删除、重命名、生成物或二进制文件 | 先给出方案请用户确认再提交 |
| 改动量很大且模块边界模糊 | 先给拆分方案请用户确认，不擅自归类 |

## 提交信息结构

结构、格式要求、常用类型与 scope 及示例，**以项目 `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

```text
<type>(<scope>): <一句话中文标题>

<正文（可选，推荐）：分点说明改了什么、为什么>

<footer（按需）>
```

- type 取 `feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `chore` 等常规类别；scope 取模块或技能名，无明确归属可省略
- 正文用中文分点说明；`fix` 类推荐按「问题现象 → 原因分析 → 修改方案 → 涉及文件」组织
- **正文分点用动词开头，禁止冒号分隔式行**：每条以「补 / 修 / 改 / 新增 / 收敛 / 同步」等动词起句；`Feature: xxx` 这类冒号分隔的行不是分点、是伪标题，不要写
- **首行控制在 50 字符以内**（含 `type(scope):` 前缀；Git 生态通行的 50/72 惯例，中文标题同样按字符数计）：超出时把细节移入正文，不靠拉长标题承载信息；正文每行不超过 72 字符
- **标题与正文之间、正文与 footer 之间各留一个空行**：缺空行时 git 会把正文并进标题——`git log --format='%s'` 显示成一行、`%b` 为空
- **多行提交信息优先落文件再提交**：用 Write 写一份消息文件后 `git commit -F <文件>`；内联 heredoc 承载多行文本时偶发丢空行，不要依赖
- **不携带任何 `Co-Authored-By` 类署名**（除非项目规范明确要求）
- 描述聚焦改动本身，不掺杂无关背景

## 可选能力

以下为可选项，**仅在用户明确提出时启用**；未提出时按上面的默认路径执行。

### 仅用 Git 的轻量路径

不依赖任何包管理器 / 构建工具，只经 git 完成提交（读改动 → 判断拆分 → `git add` → 写消息 → `git commit -F`）。适用于仓库没有构建工具、或用户明确要求"只用 git 提交"的场景。

### 显式指定 type / scope

用户指定了类型或作用域时，**覆盖**自动推断的结果写入标题；只给一个时，另一个仍按改动推断。

### emoji 前缀

用户要求提交信息带 emoji 时按 type 取前缀（**默认不带 emoji**）：

- ✨ `feat`、🐛 `fix`、📝 `docs`、🎨 `style`、♻️ `refactor`、⚡️ `perf`
- ✅ `test`、🔧 `chore`、👷 `ci`、⏪️ `revert`
- 变体：🔥 删除代码 / 文件、🚑️ 紧急修复、👽️ 适配外部 API 变更、🔒️ 安全修复、💥 破坏性变更

### 脚注（trailer）

- **破坏性变更**必须写明：正文之后空一行写 `BREAKING CHANGE: <说明>`，或在 type 后加 `!`（如 `feat!:`）。
- 其它脚注用 git trailer 形式（`Closes #123`、`Refs: #456`），与正文之间同样空一行。

### 修补上次提交（`--amend`）

用户要求"补进上一次提交"时用 `git commit --amend -F <消息文件>`；**仅限未推送的本地分支**——已推送的历史不改写，确需改写时先说明影响并取得明确同意。修补后仍按「验证」复核标题与正文已分离。

### 跳过钩子（`--no-verify`）

默认**不跳过**：钩子报错时修问题本身。只有用户在本次对话中明确要求跳过时才加 `--no-verify`，并在汇报中注明"本次跳过了钩子"。

## 输入

要提交的文件路径或范围（未指定则处理当前工作区的全部改动）；可选：提交要求（拆分粒度、信息格式等）：
