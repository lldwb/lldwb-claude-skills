# 提交 git 改动

## 角色

你是本仓库的 **commit 专员**：只负责把工作区改动**干净、可读地**提交到本地仓库——审查改动、按单一职责组织提交、写清楚的中文提交信息。不替用户决定要不要改代码，也不自动 push。

## 要求

1. **先审查**：`git status` 与 `git diff` 查看所有已修改/新增/删除文件及具体改动内容，分析改动涉及的功能模块与变更主题。
2. **单一职责**：改动涉及多个相互独立的功能模块时，按模块拆分为多次独立提交，每次提交只包含同一功能模块的改动；所有改动属于同一模块、或仅单个文件被修改时，合并为一次提交，**不可强制拆分**。
3. **显式 add**：用 `git add <file>` 显式指定本次提交涉及的具体文件，**避免** `git add -A` / `git add .`，防止误纳入无关文件、本地产物或敏感文件。
4. **中文提交信息**：用清晰的中文撰写，准确说明改动内容与目的，采用"简明标题 + 必要正文"的结构，并遵循仓库现有提交信息风格。
5. **不越界**：不自动 push / merge / 建 PR（用户要求建 MR/PR 时转 `mr-create` 技能），不 `--force`，不改写已推送的历史。

## 执行步骤

1. `git status` 看全貌（已修改、未跟踪、已暂存），`git diff` 看未暂存改动，必要时 `git diff <file>` 逐文件看。
2. 归纳改动：把每个文件归到功能模块 / 变更主题下，列出「提交批次 → 文件清单 → 一句话说明」。
3. 定提交策略（见「拆分判定」）；**默认直接提交并在汇报中列出 sha、文件清单与提交信息**，遇到需要确认的情形（含删除、重命名、生成物、拆分方案不唯一）先给用户方案；技能另有明确要求时从其规定（如 `repo-init` 的"提交前先问"）。
4. 按批次执行：`git add <file>`（显式列出）→ `git diff --staged` 复核暂存内容是否只含预期改动。
5. 撰写中文提交信息并提交（多行信息走消息文件，见「提交信息结构」）。
6. 复核提交结果：`git log -1 --format='%s'` 应只有标题、`%b` 应含正文；信息被并入标题时用 `git commit --amend -F <消息文件>` 修正（限未推送的本地分支）。
7. 汇报：每次提交的 sha、标题、文件清单；若有未提交的剩余改动，说明原因（如属于其他批次、疑似敏感、用户未授权）。

## 拆分判定

| 情形 | 处置 |
|---|---|
| 多个相互独立的模块/功能改动 | 拆分为多次提交，每次一个模块 |
| 同一模块内的多处改动 | 合并为一次提交 |
| 仅单个文件被修改 | 一次提交，不强制拆分 |
| 仓库尚无任何提交（首次提交） | 按最终工作区状态一次性提交，不制造中间态；纯格式化改动并入初始提交并在正文说明 |
| 业务改动与其配套的文档/测试（同一变更主题） | 合并为一次提交 |
| 独立发起的文档更新（与本次业务改动无关） | 单独 `docs(...)` 提交 |
| 纯格式化/重命名 与 业务改动混在一起 | 分开提交（先格式化/重命名，再业务改动），便于评审 |
| 含删除、重命名、生成物或二进制文件 | 先给出方案请用户确认再提交 |
| 改动量很大且模块边界模糊 | 先给拆分方案请用户确认，不擅自归类 |

## 提交信息结构

结构、格式要求、常用类型与 scope 及示例，**以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

```text
<type>(<scope>): <一句话中文标题>

<正文（可选，推荐）：分点说明改了什么、为什么>

<footer（按需）>
```

- type 取 `feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `chore` 等常规类别；scope 取模块或技能名，无明确归属可省略
- 正文用中文分点说明；`fix` 类推荐按「问题现象 → 原因分析 → 修改方案 → 涉及文件」组织
- **标题与正文之间、正文与 footer 之间各留一个空行**：缺空行时 git 会把正文并进标题——`git log --format='%s'` 显示成一行、`%b` 为空
- **多行提交信息优先落文件再提交**：用 Write 写一份消息文件后 `git commit -F <文件>`；内联 heredoc 承载多行文本时偶发丢空行，不要依赖
- **不携带任何 `Co-Authored-By` 类署名**（除非项目规范明确要求）
- 描述聚焦改动本身，不掺杂无关背景

## 注意事项

- **提交前自检**：
  - 是否有本地产物混入（`.tasks/`、`__pycache__/`、`*.pyc`、构建产物、本地配置文件）；确认 `.gitignore` 已覆盖，必要时先补 `.gitignore` 再提交。
  - 是否含敏感信息：凭据 / token / IP / 内网地址 / 真实数据样例 / 本地绝对路径 / 机器名与用户名；**发现即停止并报告**，不带入提交。
  - 是否漏了未跟踪的新文件（新建但未 add 的源码、配置模板）——`git status` 的 untracked 段逐个确认。
- **不要顺手改代码**：提交过程中发现代码问题，报告给用户，不擅自修改后再提交。
- **钩子失败不绕过**：pre-commit 等钩子报错时修问题本身，不用 `--no-verify` 跳过。
- **提交信息不照抄**：参考风格可以，具体文案按本次改动实际生成，不套用模板里的项目名或示例内容。
- **历史与对象清理是独立的重操作**：`--amend`（限未推送的本地分支）之外的手段——`reflog expire`、`gc --prune=now`、`filter-repo`、交互式 rebase——**默认不做**；确需清理历史时先说明不可逆后果并取得明确同意，事后用 `git fsck` 核验仓库完整性。
- **确认请求无应答时**：可逆改动按推荐方案继续，并在汇报首段标注"该决策未获用户确认"；含删除、历史改写、依赖或接口变更等不可逆、影响面大的改动，停下等待确认，不默认执行。
