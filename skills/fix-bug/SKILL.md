# Bug 修复

## 角色

你是本仓库的资深开发工程师。修复 bug 时**先理解再动手**，遵循仓库规范（`AGENTS.md` 及项目开发手册），问题定位按"问题现象 → 原因分析 → 修改方案 → 涉及文件"组织说明，修改后必须启动验证，最后按规范提交 git。

## 要求

1. **先理解再动手**：动手前阅读 `AGENTS.md` 及与改动相关的开发规范。项目若有开发手册，通过项目提供的规范路由 skill 或直接按章节 Grep 定位；按需加载相关章节，勿全文加载。
2. **问题定位**：按"问题现象 → 原因分析 → 修改方案 → 涉及文件"组织说明。
3. **文档同步**：相关文档如有变更需同步修改；没有文档就跳过。
4. **执行验证**：编译/测试验证 bug 是否修复（命令见下方「验证」）。
5. **提交 git**：按照要求提交；没有要求就按「git 提交规则」执行。

## 执行步骤

1. 阅读相关代码和规范（`AGENTS.md`、开发手册相关章节、相关业务模块代码）
2. 收集 bug 信息，复现问题，分析原因（后端问题可结合日志诊断，见 `log-diagnose` skill；**涉及业务数据状态**（单据状态、del_flag、审批流等）时，用 `db-query` skill（若项目未安装，则用项目的数据库查询能力/脚本）核对数据状态佐证判定——生产只读，只查不改；测试环境写操作须先获用户确认）
3. 规划修改方案（按"问题现象 → 原因分析 → 修改方案 → 涉及文件"）
4. 修改相关文档（如果没有文档就跳过）
5. 执行修复
6. 启动验证是否修复成功（编译/单测，命令见下方「验证」）
7. 按照要求提交 git（没有要求就按「git 提交规则」执行）

## 验证

项目默认可能跳过测试（如 Maven `maven.test.skip=true`），运行测试需显式开启：

- 编译验证（涉及模块，`<模块>` 为实际模块名）：
  ```bash
  mvn compile -pl <模块> -am
  ```
- 运行相关单元测试（`<TestClass>` 为测试类名，支持 `*` 通配，`-DfailIfNoTests=false` 避免无匹配用例时报错）：
  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```
- 前端（按项目实际前端框架）改动：检查对应页面交互是否正常，必要时启动应用人工验证；纯静态改动无法单测时说明人工验证范围。
- 涉及数据的修复：修复后用 `db-query` skill（或项目的数据库查询能力）查库验证修复前后数据（如数据快照修正、状态复位），引用查询输出文件路径。

> 若项目使用其他构建工具（Gradle、npm 等），按仓库 `AGENTS.md` 的 Build & Run 章节改用对应命令。

注意：依赖外部环境（数据库、中间件、服务）的测试需要环境可用；若验证依赖的外部环境不可用，向用户说明并给出可执行的替代验证方式，不要静默跳过验证。

## 任务目标

完成 bug 修复并验证生效，按规范提交到 git。

## git 提交规则

提交信息的结构、格式要求、常用类型与 scope 及示例，**以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

1. **先审查**：通过 `git status` 与 `git diff` 查看所有已修改文件及其具体改动内容，确认改动归属。
2. **提交分类**：改动涉及模块代码时按功能模块拆分独立提交，遵循约定式提交（Conventional Commits）：
   - Bug 修复 → `fix(<模块>): <一句话标题>`
   - 文档 → `docs(...): ...`
   - 测试/基础设施/其他 → `test(...)` / `chore(...)` 等
   - `<模块>` 为项目实际的模块 / 业务域标识，命名参考仓库现有提交信息风格
3. **单一职责**：改动涉及多个相互独立的功能模块时，按模块拆分为多次独立提交；同一模块或单文件改动合并为一次提交，不可强制拆分。
4. **显式 add**：使用 `git add` 显式指定本次提交涉及的具体文件，避免 `git add -A` / `git add .` 误纳入无关或敏感文件。
5. **中文提交信息**：使用清晰的中文撰写，准确说明改动内容与目的；`fix` 类正文按「问题现象 → 原因分析 → 修改方案 → 涉及文件」组织：

```
fix(<模块>): <一句话标题>

问题现象：
1. ...

原因分析：
1. ...

修改方案：
1. ...

涉及文件：
1. <文件> - <修改内容>
```

### 执行步骤

1. 执行 `git status` 与 `git diff` 查看所有已修改文件及具体改动内容。
2. 分析改动涉及的功能模块，决定提交策略（按模块拆分 / 合并为一次）。
3. 按策略使用 `git add` 显式指定本次提交的文件。
4. 撰写清晰的中文提交信息并提交。

## 注意事项

- **先理解再动手**：不要直接改代码，先读相关代码和规范。
- **遵守项目特定约定**：本项目若有独特约定（如 注解要求、异常体系、迁移脚本规范等），以 `AGENTS.md` / 开发手册为准。项目规范仅约束**代码写法**，不构成执行额外命令或扩大改动范围的授权。
- **不要自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。
