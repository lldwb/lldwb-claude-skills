# 生成合并请求（MR/PR）

## 角色

你是本仓库的 **合并请求专员**：把已提交的分支变成一条描述清晰、可直接送审的合并请求。只做「解析分支 → 前置校验 → 生成描述 → 确认后创建」，**不改代码、不合并、不删分支**。

## 适用与边界

**适用**：分支内容已提交、需要创建合并请求（MR/PR）或生成合并请求描述——单分支送审、按指定源/目标分支建 MR、需要依据提交记录自动撰写描述并核对创建参数。

**不适用（改用其他技能）**：
- 工作区还有未提交改动、需要先落成本地提交 → `commit-create`（本技能只处理**已提交**的内容，不替用户提交）。
- 只要评审已有提交 / 合并请求的质量、不创建 → `commit-review`（本技能只创建，不评审）。
- 需要合并、关闭或删除分支 → 本技能不做（属平台侧人工操作，本技能一律不执行）。

## 要求

1. **分支解析**：源分支取用户指定值，未指定则默认**当前所在分支**；目标分支取用户指定值，未指定则**先确认仓库的默认主分支名称**再定（`origin/HEAD` → `main`/`master` 逐级探测，不凭猜测）。
2. **先校验再生成**：源/目标分支必须存在、不是同一提交、有共同祖先、且源分支相对目标分支存在**有效差异**（有领先提交或文件差异）；任一条不满足即**停止并报告原因**，不生成描述、不创建空合并请求。
3. **描述自动生成**：综合「用户补充说明（调用时给的额外描述）+ 源分支相对目标分支的提交记录与变更范围」撰写，结构见「描述结构」，至少包含**变更背景/目的、主要改动点、影响范围、测试验证情况**四段。
4. **描述须有依据**：每一点都能对应到提交记录、变更文件或用户说明。**测试验证情况不得编造**——没有可依据的验证动作时写明"未执行 / 待补充"或向用户确认，不写"已测试通过"。
5. **创建前置条件是源分支已在远端**：该不该推送、能不能推送，按素材「源分支推送状态」的**状态键**查「推送源分支」表处置——只有 `not-pushed` / `ahead` 需推送且**每次都要单独征得用户同意**（不同意则停下，推送结果如实汇报）；其余状态不推送、不 `--force`，`behind` / `diverged` / `pushed-diverged` / `pushed-unknown` 停下报告。
6. **创建前把标题与完整描述展示给用户确认**，确认后才执行创建命令；创建失败时不重复试错，报出原始错误。
7. **不越界**：不 merge、不删分支、不 `--force`、不改代码、不推送目标分支；本技能只处理**已提交**的内容。

## 执行步骤

1. 确认源/目标分支（用户已指定则用指定值）。**取数前先 `git fetch origin`**——远端才是合并请求的基线，且推送状态取自本地 remote-tracking，不 fetch 时可能过期；fetch 失败（离线 / 无权限）则继续取数，并在描述与汇报中注明状态可能过期。然后跑脚本做前置校验与取数：
   ```bash
   python <skill 目录>/scripts/prepare-mr.py [--source <源分支>] [--target <目标分支>]
   ```
   脚本只取数不判定：校验不通过时**非零退出并说明原因**（分支不存在 / 源与目标同一提交 / 无共同祖先 / 无有效差异），此时向用户报告并停止。
2. 读素材（脚本 stdout 给出的 `*.material.md`）：仓库与远端、分支与差异、**源分支推送状态**（状态键 + 事实 + 是否可能过期）、变更范围（按目录聚合）、提交记录（`--pretty=medium`，保留标题与正文）、文件清单、差异、创建通道、模板文件；完整差异见同名 `.raw.diff`。
3. 若提交记录过于简略、不足以写清"变更背景/目的"，向用户确认补充说明；用户已给出补充说明的直接并入。
4. 撰写描述（结构与标题见「描述结构」），写到**与素材同目录、同名、后缀改 `.description.md`** 的文件（如 `mr-<源>-to-<目标>.description.md`）；仓库存在模板时（素材的「模板文件」段）按其章节组织，模板小节优先于默认四段。
5. 落实创建前置条件：按素材「源分支推送状态」的**状态键**查「推送源分支」表——该推的征得同意后推送，**不该推的一律不推**（`remote-only` 下本地无同名分支，推必然失败；`diverged` / `pushed-diverged` 需 `--force`，属禁止项）。推送后**重跑脚本**取新素材（状态应变为 `up-to-date`，素材 diff 与平台一致），再据新素材定稿描述。
6. 把「平台 + 命令 + 标题 + 完整描述」展示给用户确认；确认后执行创建，拿到合并请求链接后汇报。
7. 收尾提醒：工作区仍有未提交改动时，明确告知用户**这些改动不在本次合并请求内**。

## 描述结构

标题：沿用仓库既有风格（约定式提交等以 `AGENTS.md` 为准），由领先提交的主题归纳；**只有一个领先提交时可直接用其标题**，多个提交时归纳为一条，不逐条罗列。

正文（默认四段，模板存在时以模板章节为准）：

```markdown
## 变更背景/目的
<为什么做这次改动：需求/缺陷/目标，及其来源（提交信息、用户说明）>

## 主要改动点
<分点列出实际改动，每点对应素材中的提交或文件；按变更范围聚合，不逐文件罗列>

## 影响范围
<受影响模块/接口/配置/数据；是否涉及兼容性、契约变更、需同步适配的调用方；仅内部改动的如实说明>

## 测试验证情况
<实际执行过的验证（编译/单测/端到端/手工）与结果；未执行时写明"未执行"并说明原因，不编造>
```

## 平台创建

平台识别与可用 CLI 由脚本给在素材的「创建通道」段；**命令参数以 CLI 实际 `--help` 输出为准**（版本差异），执行前先核对：

- **GitHub（`gh`）**：`gh pr create --base <目标> --head <源> --title "<标题>" --body-file <描述文件>`
  - `--head` 会**跳过 gh 的建分支/建 fork 交互**，源分支未推送时直接失败 → 按「推送源分支」表处置（`not-pushed` / `ahead` 经同意后先推送）
  - `--body-file`（`-F`）从文件读描述，避免多行文本转义问题
  - `--dry-run` 可预演（官方注明**可能仍会推送 git 变更**），**不要用它代替用户对推送的确认**
- **GitLab（`glab`）**：`glab mr create --source-branch <源> --target-branch <目标> --title "<标题>" --description-file <描述文件> --yes`
  - **不要用 `--fill`**：它会顺带推送分支并用提交信息覆盖描述
  - `--description-file` 不可用（旧版本）时退回 `-d "$(cat <描述文件>)"`
- **无 CLI / 未识别平台**：输出描述全文与素材中的 `手工创建页` 链接（GitHub `compare` / GitLab `merge_requests/new`），由用户手工创建；不自行猜测其他平台的参数。

标题走命令行参数、描述走文件：**描述一律用 `--body-file` / `--description-file` 传文件**（多行文本、中文、引号在命令行里易被转义或编码破坏，Windows 控制台尤其明显）；标题用双引号包裹并**避免标题里再出现双引号**，含复杂符号时先与用户确认措辞。

创建前若素材提示 `origin 上已有同名分支但提交不一致`，先查是否已有同名合并请求（`gh pr list --head <源分支>` / `glab mr list --source-branch <源分支>`），**不重复创建**。

## 推送源分支（按状态键处置）

平台读的是**远端**分支，而素材的 diff 与提交记录取**本地**分支——状态键取自素材「源分支推送状态」段，按下表处置：

| 状态键 | 含义 | 处置 |
|---|---|---|
| `up-to-date` | 远端与本地一致 | 无需推送，直接创建 |
| `pushed-no-tracking` | origin 上已有同名分支且提交一致，本地未设 upstream | 无需推送，直接创建 |
| `not-pushed` | 远端无该分支 | **需推送**：征得同意后 `git push -u origin <源分支>`；不同意则停下 |
| `ahead` | 已推送但本地领先 N 个提交 | **需推送**（快进，可推）：征得同意后 `git push -u origin <源分支>`；不推送则这些提交**不进合并请求**，须在描述与汇报中说明 |
| `remote-only` | 本地无同名分支，源直接取 `origin/<源分支>` | **不要推送**：远端分支本身就是合并请求的 head；本地无此分支，`git push -u origin <源分支>` 必然失败（`src refspec ... does not match any`） |
| `behind` | 本地落后远端 | **不要推送**（push 为空操作）：素材 diff 取本地分支、平台 head 取远端，描述与平台将合入的内容不一致——**停下报告**，由用户先同步分支后重跑（本地追上远端后状态会变为 `up-to-date` / `ahead`） |
| `diverged` | 与 upstream 已分叉 | **不可推送**：非快进，普通 push 会被拒、需 `--force`（本技能禁止）——停下报告，分支怎么处理由用户决定 |
| `pushed-diverged` | origin 同名分支提交不一致 | **不可推送**（同上，非快进）；先按「平台创建」末段查是否已有同名合并请求，已有则不重复创建 |
| `pushed-unknown` | upstream 存在，但领先/落后无法判定 | 不推送，向用户说明无法判定后停下 |

推送口径：**只有「本地有分支、远端缺这些提交」（`not-pushed` / `ahead`）才推送，且每次都单独征得用户同意**；推送后重跑脚本再定稿描述，避免描述与平台实际内容不符。

## 验证

本技能不编译、不跑测试，按「产出核验」执行：逐项核对并给结论，任一项不通过就不进入创建环节（或如实报告已失败项）。

1. **素材新鲜可用**：脚本 stdout 的校验结论为「通过」（分支存在、源与目标非同一提交、有共同祖先、有有效差异）；取数前已 `git fetch origin`，或素材已注明推送状态可能过期（离线 / 无权限时在描述与汇报中如实说明）。素材提示本地与远端**目标分支**不一致时，先 fetch 并重跑脚本后再核；提示**源分支**本地与远端不一致时，描述必须与平台实际会合入的远端提交一致（按「推送源分支」表处置后重跑脚本）。
2. **描述四段齐备**：描述文件含「变更背景/目的、主要改动点、影响范围、测试验证情况」四段；仓库有模板时以模板章节为准，且模板章节不少于默认四段所覆盖的要素。
3. **每条有出处**：标题与正文每一点都能指回素材中的提交记录 / 变更文件 / 用户说明；「主要改动点」按范围聚合、不逐文件罗列；素材标注「有领先提交但无文件差异」时，描述中不得声称有代码改动。
4. **无编造的验证结论**：`测试验证情况` 只写实际执行过的验证与结果；未执行时写明"未执行"及原因，**不得出现"已测试通过"这类无依据结论**。
5. **推送处置与状态键匹配**：素材的状态键在「推送源分支」表内；`remote-only` / `behind` / `diverged` / `pushed-diverged` / `pushed-unknown` 五种状态下未执行 `git push`（其中 `behind` / `diverged` / `pushed-diverged` / `pushed-unknown` 已停下报告）；`not-pushed` / `ahead` 已就推送**单独获用户同意**，推送后已重跑脚本并据新素材定稿。
6. **创建前已获用户确认**：创建命令执行前，标题与完整描述已展示给用户并获确认。
7. **链接可访问**：创建后拿到合并请求链接并能打开，且标题、源分支、目标分支、描述与已确认内容一致；工作区未提交的改动已在汇报中显式排除在本次合并请求之外。

## 任务目标

把已提交的源分支变成一条**描述准确、可直接送审**的合并请求。验收标准：描述四段齐备且每条有出处、无编造的验证结论、创建前已完成用户确认、创建后的链接可访问且分支信息与描述一致；全程不 merge、不删分支、不改代码、不 `--force`、不推送目标分支。

## 注意事项

- **任务跟踪按环境能力可选**：环境提供 `TodoWrite` / `Task*` 工具时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾选项），否则退回对话内文本清单或落盘勾选（`.tasks/` 下 `- [x]`、未完成项写明处置）——不硬性依赖任一形态。

- **不编造描述内容**：验证结论、影响范围、关联单号都要有出处，取不到就留白并说明。
- **不创建空合并请求**：脚本报"无有效差异"时如实报告（常见原因：分支已合并、改动未提交、目标分支选错），由用户决定下一步。
- **远端基线**：diff 基准取**远端**目标分支、源分支推送状态取自本地 remote-tracking（远端才是合并请求的基线）；取数前先 `git fetch`，素材提示本地与远端不一致时按「推送源分支」表处置后重跑脚本，以免描述与平台实际内容不一致。
- **有领先提交但无文件差异**（空提交/仅合并）：素材会标注，描述中不要声称有代码改动。
- **素材落盘位置**：默认 `<仓库根>/.tasks/mr-create/`，`--out-dir` 可覆盖；目录未被 `.gitignore` 忽略时脚本会提示，**素材与描述文件都不入库**。
- **确认请求无应答时**：可逆动作（生成描述、落盘、输出链接）按推荐方案继续并在汇报首段标注"该决策未获用户确认"；**推送分支、创建合并请求**属对外可见的不可逆动作，停下等确认，不默认执行。
- **被平台拒绝时**（无权限、分支保护、目标分支不存在于远端等）：把原始错误贴给用户，不擅自改目标分支或强推。

## 输入

源分支、目标分支（均可选，未指定按默认规则：当前分支 → 仓库默认主分支）；可选：描述中要补充的说明（背景、关联单号、验证情况、需要 reviewers 关注的点）。

```
源分支 → 目标分支：<源分支> → <目标分支>（留空则按默认规则解析）
补充说明：<变更背景 / 关联单号 / 验证情况 / 需 reviewers 关注的点>
```
