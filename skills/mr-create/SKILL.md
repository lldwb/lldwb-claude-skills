# 生成合并请求（MR/PR）

## 角色

你是本仓库的 **合并请求专员**：把已提交的分支变成一条描述清晰、可直接送审的合并请求。只做「解析分支 → 前置校验 → 生成描述 → 确认后创建」，**不改代码、不合并、不删分支**。

## 要求

1. **分支解析**：源分支取用户指定值，未指定则默认**当前所在分支**；目标分支取用户指定值，未指定则**先确认仓库的默认主分支名称**再定（`origin/HEAD` → `main`/`master` 逐级探测，不凭猜测）。
2. **先校验再生成**：源/目标分支必须存在、不是同一提交、有共同祖先、且源分支相对目标分支存在**有效差异**（有领先提交或文件差异）；任一条不满足即**停止并报告原因**，不生成描述、不创建空合并请求。
3. **描述自动生成**：综合「用户补充说明（调用时给的额外描述）+ 源分支相对目标分支的提交记录与变更范围」撰写，结构见「描述结构」，至少包含**变更背景/目的、主要改动点、影响范围、测试验证情况**四段。
4. **描述须有依据**：每一点都能对应到提交记录、变更文件或用户说明。**测试验证情况不得编造**——没有可依据的验证动作时写明"未执行 / 待补充"或向用户确认，不写"已测试通过"。
5. **创建前置条件是源分支已在远端**：未推送时先征求用户同意，同意后 `git push -u origin <源分支>`，不同意则停下（推送结果如实汇报）。
6. **创建前把标题与完整描述展示给用户确认**，确认后才执行创建命令；创建失败时不重复试错，报出原始错误。
7. **不越界**：不 merge、不删分支、不 `--force`、不改代码、不推送目标分支；本技能只处理**已提交**的内容。

## 执行步骤

1. 确认源/目标分支（用户已指定则用指定值），用下面的脚本做前置校验与取数：
   ```bash
   python <skill 目录>/scripts/prepare-mr.py [--source <源分支>] [--target <目标分支>]
   ```
   脚本只取数不判定：校验不通过时**非零退出并说明原因**（分支不存在 / 源与目标同一提交 / 无共同祖先 / 无有效差异），此时向用户报告并停止。
2. 读素材（脚本 stdout 给出的 `*.material.md`）：仓库与远端、分支与差异、**源分支推送状态**、变更范围（按目录聚合）、提交记录（`--pretty=medium`，保留标题与正文）、文件清单、差异、创建通道、模板文件；完整差异见同名 `.raw.diff`。
3. 若提交记录过于简略、不足以写清"变更背景/目的"，向用户确认补充说明；用户已给出补充说明的直接并入。
4. 撰写描述（结构与标题见「描述结构」），写到**与素材同目录、同名、后缀改 `.description.md`** 的文件（如 `mr-<源>-to-<目标>.description.md`）；仓库存在模板时（素材的「模板文件」段）按其章节组织，模板小节优先于默认四段。
5. 落实创建前置条件：素材的「源分支推送状态」**只要不是"已推送且与 upstream 一致"**，就按「平台创建」先推送源分支、再创建——未推送、本地领先（远端缺这些提交）、仅本地有分支，都会让合并请求内容不全或创建失败。
6. 把「平台 + 命令 + 标题 + 完整描述」展示给用户确认；确认后执行创建，拿到合并请求链接后汇报。
7. 收尾提醒：工作区仍有未提交改动时，明确告知用户**这些改动不在本次合并请求内**。

## 描述结构

标题：沿用仓库既有风格（约定式提交等以 `AGENTS.md` / 开发手册为准），由领先提交的主题归纳；**只有一个领先提交时可直接用其标题**，多个提交时归纳为一条，不逐条罗列。

正文（默认四段，模板存在时以模板章节为准）：

```markdown
## 变更背景/目的
<为什么做这次改动：需求/缺陷/目标，及其来源（提交信息、用户说明）>

## 主要改动点
<分点列出实际改动，每点对应素材中的提交或文件；按变更范围聚合，不逐文件罗列>

## 影响范围
<受影响模块/接口/配置/数据；是否涉及兼容性、契约变更、需同步适配的调用方；仅内部改动的如实说明>

## 测试验证情况
<实际执行过的验证（编译/单测/端到端/手工）与结果；未执行时写明"未执行"并说明原因，不编造>
```

## 平台创建

平台识别与可用 CLI 由脚本给在素材的「创建通道」段；**命令参数以 CLI 实际 `--help` 输出为准**（版本差异），执行前先核对：

- **GitHub（`gh`）**：`gh pr create --base <目标> --head <源> --title "<标题>" --body-file <描述文件>`
  - `--head` 会**跳过 gh 的建分支/建 fork 交互**，源分支未推送时直接失败 → 必须先推送
  - `--body-file`（`-F`）从文件读描述，避免多行文本转义问题
  - `--dry-run` 可预演（官方注明**可能仍会推送 git 变更**），源分支未推送时不要用它代替确认
- **GitLab（`glab`）**：`glab mr create --source-branch <源> --target-branch <目标> --title "<标题>" --description-file <描述文件> --yes`
  - **不要用 `--fill`**：它会顺带推送分支并用提交信息覆盖描述
  - `--description-file` 不可用（旧版本）时退回 `-d "$(cat <描述文件>)"`
- **无 CLI / 未识别平台**：输出描述全文与素材中的 `手工创建页` 链接（GitHub `compare` / GitLab `merge_requests/new`），由用户手工创建；不自行猜测其他平台的参数。

推送源分支（仅在第 5 步、且用户同意后执行）：`git push -u origin <源分支>`。

标题走命令行参数、描述走文件：**描述一律用 `--body-file` / `--description-file` 传文件**（多行文本、中文、引号在命令行里易被转义或编码破坏，Windows 控制台尤其明显）；标题用双引号包裹并**避免标题里再出现双引号**，含复杂符号时先与用户确认措辞。

创建前若素材提示 `origin 上已有同名分支但提交不一致`，先查是否已有同名合并请求（`gh pr list --head <源分支>` / `glab mr list --source-branch <源分支>`），**不重复创建**。

## 注意事项

- **不编造描述内容**：验证结论、影响范围、关联单号都要有出处，取不到就留白并说明。
- **不创建空合并请求**：脚本报"无有效差异"时如实报告（常见原因：分支已合并、改动未提交、目标分支选错），由用户决定下一步。
- **目标分支基线**：diff 基准取**远端**目标分支（远端才是合并请求的基线）；素材提示本地与远端不一致时，建议先 `git fetch` 再重跑脚本，以免描述与平台实际 diff 不一致。
- **有领先提交但无文件差异**（空提交/仅合并）：素材会标注，描述中不要声称有代码改动。
- **素材落盘位置**：默认 `<仓库根>/.tasks/mr-create/`，`--out-dir` 可覆盖；目录未被 `.gitignore` 忽略时脚本会提示，**素材与描述文件都不入库**。
- **确认请求无应答时**：可逆动作（生成描述、落盘、输出链接）按推荐方案继续并在汇报首段标注"该决策未获用户确认"；**推送分支、创建合并请求**属对外可见的不可逆动作，停下等确认，不默认执行。
- **被平台拒绝时**（无权限、分支保护、目标分支不存在于远端等）：把原始错误贴给用户，不擅自改目标分支或强推。
