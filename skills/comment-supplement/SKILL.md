# 注释补齐与修正

## 角色

你是本仓库的资深开发工程师。任务**严格限定在注释层面**：补全缺失的注释、修正不准确/过期/与代码实际行为不符的描述。好的注释写"为什么"与"约束条件"，而不是复述代码字面意思。

## 铁律

1. **只动注释**：不修改任何业务逻辑、方法签名、字段名、注解、默认值与可执行代码；改动只允许落在注释文本内。
2. **不确定不臆测**：无法从现有代码判断真实意图时，整理成清单交用户确认，确认后再写。

## 要求

1. **补全**：类 / 方法 / 字段缺失的说明，按项目注释规范补齐标签（如 `@param` / `@return` / `@throws` / `@author` 等）。
2. **修正**：不准确、过期、与代码实际行为不符的描述——参数说明与实际不符、抛出的异常未写、返回值语义变了没同步、被注释掉的废弃代码块、复制粘贴留下的错别字。
3. **语言与风格**：遵循项目现有注释规范（中文/英文、句式、必填标签）；无规范则与同文件既有注释保持一致。
4. **不写废话注释**：不写"get 方法获取 X""设置 Y"这类复述代码的注释；不写 TODO 式占位或含义不明的注释。

## 执行步骤

1. 通读目标文件/目录，理解整体结构与业务逻辑（含调用链、相关常量与配置）。
2. 逐文件审查现有注释，标记三类位置：**缺失** / **不准确** / **过期**。
3. 整理不确定项清单（位置 + 存疑点 + 无法判断的原因），**先交用户确认**。
4. 按确认结果补全与修正注释（仅注释层面）。
5. 自检（见「自检」），确认未改动任何逻辑代码。
6. 汇报修改清单与结果（改了哪些文件、多少处、不确定项如何处置），按「git 提交规则」提交。

## 自检

- `git diff` 逐块核对：每个 hunk 是否都落在注释块内（`/** ... */`、`//`、`<!-- -->`、`#` 等）。
- `git diff -w`（忽略空白）辅助判断：忽略空白后差异消失，说明只动了排版/缩进；仍有差异的块逐个确认。
- 编译/构建验证：注释改动不应改变编译结果，编译通过可确认未破坏语法（命令见项目 `AGENTS.md` 的 Build & Run 章节）。
- 汇报给「已改文件 + 处数 + 不确定项处置」三件套，不用"已完成"这类空泛结论收尾。

## 注意事项

- **只改注释，不改代码**：发现代码缺陷单独报告（需修复时转 `bug-fix`），不在本流程里顺手改逻辑。
- **与 `bug-fix` 的分工**：改动**仅**落在注释层面 → 本技能；注释问题与逻辑、结构、接口改动并存 → `bug-fix` 一并处理（本技能的铁律"只动注释"不允许在同一提交里混入代码改动）。
- **不动公开契约**：签名、注解、默认值、枚举取值一律不动，即使注释里写的内容与它们冲突（冲突项列入不确定清单）。
- **大范围任务分批**：目标文件较多时按目录/模块分批处理，便于用户逐批确认。
- **不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。

## git 提交规则

提交信息的结构、格式要求与类型，**以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

1. **先审查**：`git status` 与 `git diff` 查看改动，确认全部落在注释内。
2. **显式 add**：`git add <file>` 显式指定文件，**禁止** `git add -A` / `git add .`。
3. **中文提交信息**：遵循约定式提交，注释类改动用 `docs(<模块>): 补全/修正 <范围> 注释`，正文分点说明补全与修正的内容；若同时修改了业务代码，业务改动必须单独提交。
