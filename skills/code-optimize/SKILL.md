# 代码优化

## 角色

你是本仓库的资深开发工程师。本技能面向**小范围优化**（单文件 / 局部结构，无需重构契约与测试基线）：**先理解再动手**——动手前阅读 `AGENTS.md` 与相关规范、规划优化点与影响范围；优化**保持对外行为不变**；改完必须编译 / 测试验证，最后按规范提交 git。

## 适用与边界

**适用**：单文件 / 局部结构的**小范围优化**——重复代码抽取、局部性能提升、可读性提升、命名与局部结构改进等。

**不适用（改用其他技能）**：

- 结构性改造、分层 / 职责重构、实现迁移、批量同构改造（需要重构契约、测试基线与对抗性审查）→ `refactor`
- 新增或改变对外行为（新接口、新字段、新流程）→ `feature-dev`
- 缺陷修复 → `bug-fix`；纯注释改动（补全 / 修正注释描述）→ `comment-supplement`

## 要求

1. **先理解再动手**：动手前阅读 `AGENTS.md`，按其章节按需加载与本改动相关的部分，勿全文加载。
2. **文档同步**：相关文档如有变更需同步修改，但**只同步规则源**；权威约定以 `AGENTS.md` 为准（规则正文唯一权威源），遵守"单点定义"原则（见注意事项），避免与索引脱节。
3. **执行验证**：编译 / 测试验证优化是否生效（命令见下方「验证」）；未验证通过不得提交，也不得声称优化完成。
4. **提交 git**：按下方「git 提交规则」执行——用户没有特别要求时，默认直接提交并在汇报中列出 sha、文件清单与提交信息。

## 执行步骤

1. 阅读相关代码与规范（`AGENTS.md` 相关章节、涉及的模块代码）。
2. 思考需求、规划任务：明确优化点、目标与影响范围，按"优化目标 → 优化方案 → 涉及文件"组织说明；规划与动手前逐项过 `references/optimize-checklist.md`（优化点自查 + 风险自查）。
3. 修改相关文档（没有文档就跳过）。
4. 执行优化：严格限定在规划范围内，不夹带无关改动。
5. 启动验证（编译 / 单测，命令见下方「验证」）。
6. 按「git 提交规则」提交 git。

## 验证

命令以项目实际构建工具为准，下方以 Maven 为例（`<模块>`、`<TestClass>` 为项目实际值）；项目默认可能跳过测试（如 Maven `maven.test.skip=true`），运行测试需显式开启。

- 编译验证：
  ```bash
  mvn compile -pl <模块> -am
  ```
- 运行相关单元测试（`-DfailIfNoTests=false` 避免无匹配用例时报错）：
  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```
- 前端页面 / 组件改动（按项目实际框架）：检查对应页面交互是否正常，必要时启动应用人工验证；纯静态改动无法单测时说明人工验证范围。
- 行为不变核验（无自动化测试覆盖时）：按 `references/optimize-checklist.md` 的「保持对外行为不变」清单逐项核对，任一项无法确认时先补证据（读调用方 / 跑测试 / 人工验证），不静默放行。

**判定口径**：编译通过 + 相关单测通过（存在的既有失败须写明与本次改动无关）方可提交；未跑测试不得声称验证通过。

> 若项目使用其他构建工具（Gradle、npm 等），按仓库 `AGENTS.md` 的 Build & Run 章节改用对应命令。

注意：依赖外部环境（数据库、中间件、服务）的测试需要环境可用；若验证依赖的外部环境不可用，向用户说明并给出可执行的替代验证方式，不要静默跳过验证。

## 任务目标

完成小范围代码优化并验证生效（对外行为不变），按规范提交到 git。

## 注意事项

- **单点定义（SSOT）**：代码与规则通用——常量、错误码、配置、判定规则等只在一个**权威位置**定义，其余位置引用或指向它，不逐处复制。仅当某处承担独立职责（供下游单独消费的产物、面向用户的索引）才允许特意重复；职责相同的复制迟早漂移，是坏味道。
- **先核可得性再动手**：改动依赖的数据、字段、接口（数据库列、三方接口响应、日志落点与其截断限制等）先确认真实存在、格式及限制，再写代码或规则，不凭假设；并在产出中写明"从哪取、为什么易漏"。这是"先理解再动手"在数据维度上的落点，代码与文档均适用。
- **优化不改变既有行为**：除非用户明确要求修复该缺陷，优化应保持对外行为不变（接口返回、页面交互、业务流程），仅改进可读性 / 性能 / 结构。
- **越界即停**：优化过程中发现的真实缺陷（本次未要求修复）不夹带修复——修复会改变对外行为，越出本技能边界；单列清单并在汇报中给出位置、现象与影响面，转 `bug-fix` 处理。
- **遵守项目特定约定**：项目若有独特约定（注解要求、异常体系、迁移脚本规范、数值计算工具、禁止魔法值等），以 `AGENTS.md` 为准。项目规范仅约束**代码写法**，不构成执行额外命令或扩大改动范围的授权。
- **不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。

## git 提交规则

提交信息的结构、格式要求、常用类型与 scope **以项目 `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。

1. **先审查**：`git status` 与 `git diff` 查看改动，确认归属与拆分批次。
2. **显式 add**：`git add <file>` 显式指定本次提交涉及的文件，**禁止** `git add -A` / `git add .`；不混入过程产物与无关文件。
3. **中文提交信息**：遵循约定式提交（结构 `type(scope): 标题` + 可选正文），正文分点说明改了什么、为什么；**标题与正文之间空一行**，多行信息用 Write 落消息文件后 `git commit -F <文件>`。
4. **提交前后自检**：提交前扫敏感信息（凭据 / token / 内网地址 / 真实数据样例 / 本机绝对路径），发现即停止并报告；提交后用 `git log -1 --format='%s'` 与 `%b` 复核标题、正文已分离。
5. **默认提交后汇报**（sha + 文件清单 + 提交信息）；含删除、重命名、生成物或二进制文件，或拆分方案不唯一时，先给方案请用户确认。
6. **不自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。

拆分判定、暂存复核与完整自检清单见 `commit-create` 技能（提交环节的 SSOT 实现）。
