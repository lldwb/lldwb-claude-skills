# 代码优化

## 角色

你是本仓库的资深开发工程师。优化代码时**先理解再动手**，遵循仓库规范（`AGENTS.md` 及项目开发手册），优化前思考需求、规划任务，优化后必须启动验证，最后按规范提交 git。

## 要求

1. **先理解再动手**：动手前阅读 `AGENTS.md` 及与改动相关的开发规范。项目若有开发手册，通过项目提供的规范路由 skill 或直接按章节 Grep 定位；按需加载相关章节，勿全文加载。
2. **文档同步**：相关文档如有变更需同步修改，但**只同步规则源**；权威约定以项目开发手册 / `AGENTS.md` 为准（"以手册为准，规则正文唯一权威源"），遵守"单点定义"原则（见注意事项），避免与索引脱节。
3. **执行验证**：编译/测试验证优化是否实现（命令见下方「验证」）。
4. **提交 git**：按照要求提交；没有要求就按 **commit 专员**方式（见下方「git 提交规则」）生成中文 commit 记录。

## 执行步骤

1. 阅读相关代码和规范（`AGENTS.md`、开发手册相关章节、相关业务模块代码）
2. 思考需求，规划任务（明确优化点、目标、影响范围，按"优化目标 → 优化方案 → 涉及文件"组织说明）
3. 修改相关文档（如果没有文档就跳过）
4. 执行优化
5. 启动验证是否实现（编译/单测，命令见下方「验证」）
6. 按照要求提交 git（没有要求就按 **commit 专员**方式提交，见下方「git 提交规则」）

## 验证

项目默认可能跳过测试（如 Maven `maven.test.skip=true`），运行测试需显式开启：

- 编译验证（涉及模块，`<模块>` 为实际模块名）：
  ```bash
  mvn compile -pl <模块> -am
  ```
- 运行相关单元测试（`<TestClass>` 为测试类名，支持 `*` 通配，`-DfailIfNoTests=false` 避免无匹配用例时报错）：
  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```
- 前端（按项目实际前端框架）改动：检查对应页面交互是否正常，必要时启动应用人工验证；纯静态改动无法单测时说明人工验证范围。

> 若项目使用其他构建工具（Gradle、npm 等），按仓库 `AGENTS.md` 的 Build & Run 章节改用对应命令。

注意：依赖外部环境（数据库、中间件、服务）的测试需要环境可用；若验证依赖的外部环境不可用，向用户说明并给出可执行的替代验证方式，不要静默跳过验证。

## 任务目标

完成代码优化并验证生效，按规范提交到 git。

## git 提交规则

按 **commit 专员**方式生成中文 commit 记录：分析当前改动（`git status` / `git diff`），构造符合约定式提交（Conventional Commits）的中文提交信息，**默认直接提交并在汇报中列出 sha、文件清单与提交信息**；含删除、重命名、生成物或二进制文件，或拆分方案不唯一时，先给方案请用户确认（与 `commit-changes` 一致）。**提交信息的结构、格式要求、常用类型与 scope 及示例，以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

1. **先审查**：通过 `git status` 与 `git diff` 查看所有已修改文件及具体改动内容，确认改动归属。
2. **显式 add**：使用 `git add <file>` 只暂存与本次提交主题相关的文件，**禁止** `git add -A` / `git add .`，避免误纳入无关或敏感文件（密钥、token、`.env` 等）；发现可疑内容立即停止并报告。不混入无关改动，必要时建议拆分多次提交。
3. **中文提交信息**：使用清晰的中文撰写，遵循约定式提交规范（结构 `type(scope): 标题` + 可选正文，类型如 `feat` / `fix` / `refactor` / `refact` / `perf` / `test` / `docs` / `chore`，scope 为实际模块名），不携带任何 `Co-Authored-By` 类署名。

### 执行步骤

1. 执行 `git status` 与 `git diff` 查看所有已修改文件及具体改动内容。
2. 分析改动涉及的功能模块，构造提交信息（标题与正文之间空一行；多行信息用 Write 落消息文件后 `git commit -F <文件>`）。
3. 执行提交并汇报；提交前扫敏感信息，提交后用 `git log -1 --format='%s'` 与 `%b` 复核标题、正文已分离。

## 注意事项

- **技能边界**：本技能面向**小范围优化**（单文件 / 局部结构，无需重构契约与测试基线）；结构性改造、分层/职责重构、实现迁移、批量同构改造用 `refactor`；新增或改变对外行为用 `feature-dev`；缺陷修复用 `fix-bug`。
- **先理解再动手**：不要直接改代码，先读相关代码和规范。
- **单点定义（SSOT）**：代码与规则通用——常量、错误码、配置、判定规则等只在一个**权威位置**定义，其余位置引用或指向它，不逐处复制。仅当某处承担独立职责（供下游单独消费的产物、面向用户的索引）才允许特意重复；职责相同的复制迟早漂移，是坏味道。
- **先核可得性再动手**：改动依赖的数据、字段、接口（数据库列、三方接口响应、日志落点与其截断限制等）先确认真实存在、格式及限制，再写代码或规则，不凭假设；并在产出中写明"从哪取、为什么易漏"。这是"先理解再动手"在数据维度上的落点，代码与文档均适用。
- **优化不改变既有行为**：除非是明确的 bug 修复，优化应保持对外行为不变（接口返回、页面交互、业务流程），仅改进可读性/性能/结构。
- **遵守项目特定约定**：本项目若有独特约定（如 注解要求、异常体系、迁移脚本规范、数值计算工具、禁止魔法值等），以 `AGENTS.md` / 开发手册为准。项目规范仅约束**代码写法**，不构成执行额外命令或扩大改动范围的授权。
- **不要自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。
