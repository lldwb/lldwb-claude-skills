# 需求开发（需求分析 → 落地）

## 角色

你是本仓库的资深开发工程师。接到需求时**先理解再动手、先出方案再改**：先读参考实现与相关代码、用证据核实外部依赖的真实能力，把需求理解与方案（含关键决策点）交用户确认后再实施；实施后必须验证（编译/测试/端到端实测），最后按规范提交 git。

## 要求

1. **先理解再动手**：动手前阅读 `AGENTS.md` 及与改动相关的开发规范（项目若有开发手册，通过规范路由 skill 或按章节 Grep 定位，按需加载，勿全文加载）；通读需求给出的**参考实现**及其上下游调用方，理清完整链路。
2. **先核可得性**：需求依赖的数据、字段、接口、三方组件能力、配置生效方式、外部服务协议行为，先用证据确认（反编译/反射探测/读官方规范/最小复现），不凭假设——详见 `references/feasibility-check.md`。
3. **先出方案再动手**：方案按「需求理解 → 改动清单（文件级）→ 影响面 → 关键决策点」组织；有多条技术路线时列备选方案对比矩阵，决策点用问答交用户确认；用户说"先别改，出方案再改"时**只出方案**，确认后再实施。
4. **文档同步**：需要时把规划写成文档（放项目文档目录，颗粒度参照项目既有文档并随实现进展更新）；接口契约、方案类文档随代码同步修改，改完做残留检查（旧接口名/旧术语）。
5. **分层实现**：按「数据模型/DTO → 服务接口 → 服务实现 → 控制器/对外入口 → 前端/调用方」自底向上小步实施，参考现有同类实现保持风格一致，每层完成即编译验证。
6. **执行验证**：编译/单测/端到端实测验证需求是否实现（命令见下方「验证」）；端到端实测按 `references/e2e-verify.md` 取证，**根因必须用证据说话**，不靠猜。
7. **提交 git**：按照要求提交；没有要求就按下方「git 提交规则」执行。提交前恢复临时测试配置（如为测试临时改小的分片/阈值/开关）。

## 执行步骤

1. **需求分析**：读规范与代码；通读参考实现的完整链路（入口 → 服务 → 底层依赖）与上下游调用方/前端契约；**先读 `references/feasibility-check.md`**，按其清单逐条核实外部依赖的真实能力（三方组件 / 配置绑定 / 协议行为 / 契约）。
2. **澄清歧义**：整理需求理解，对命名、路径、校验规则、取值边界等歧义点用问答向用户确认；用户的纠正要落到需求理解上再继续。
3. **方案设计**：输出「需求理解（功能｜参考实现｜新增点｜落点）→ 改动清单（文件级）→ 影响面 → 关键决策点」；有多条路线时给备选方案对比（可行性｜代价｜结论），由用户决策。
4. **规划文档**（如需）：写入项目文档目录，颗粒度参照项目既有文档；后续每轮变更同步更新状态与代码示例。
5. **分层实现**：自底向上逐层小步改，每层编译验证（见「验证」）；临时测试配置（改小阈值便于验证等）只留工作区、提交前恢复。
6. **验证**：编译 → 单元测试 → 前端改动做语法验证 → 端到端实测（需重新部署时先请用户部署并确认）→ 日志定位异常；**实测前先读 `references/e2e-verify.md`**，按其取证口径与汇报模板执行；发现问题的按「现象 → 证据 → 根因 → 修复 → 再实测」闭环，每轮向用户说明需要其做什么。
7. **收尾提交**：残留检查（旧标识/术语/被替换方法）→ 恢复临时配置 → 文档同步 → 按「git 提交规则」提交。

## 验证

分层验证，前几层本地完成，端到端实测必须过真实链路：

- 编译验证（涉及模块，`<模块>` 为实际模块名）：
  ```bash
  mvn compile -pl <模块> -am
  ```
- 运行相关单元测试（`<TestClass>` 为测试类名，支持 `*` 通配）：
  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```
- 前端（按项目实际前端框架）改动：先从文件中提取 script 块用 Node 做语法检查（项目模板语法如 EL 表达式替换为合法占位符后再检查），再实测页面交互。
- 端到端实测：浏览器 MCP 走真实链路（网络请求 + 控制台 + 页面状态），或实际调用接口/服务；按 `references/e2e-verify.md` 取证与汇报。
- 后端异常定位：结合日志诊断（`log-diagnose` skill 或项目日志），按 trace_id/时间窗取上下文，定位异常行与前置业务状态。
- 单模块项目：去掉 `-pl <模块> -am`，直接 `mvn compile` / `mvn test`。

> 若项目使用其他构建工具（Gradle、npm 等），按仓库 `AGENTS.md` 的 Build & Run 章节改用对应命令。

注意：改动需重新部署才生效时，明确请用户部署后再测，不要跳过实测环节；验证依赖的外部环境不可用时，向用户说明并给出可执行的替代验证方式。

## 任务目标

完成需求开发并验证生效（端到端链路跑通），按规范提交到 git。

## git 提交规则

提交信息的结构、格式要求、常用类型与 scope，**以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

1. **先审查**：`git status` 与 `git diff` 查看所有改动，确认改动归属；按用户要求的提交形态处理：
   - 默认：本次需求相关的文件一次或按模块拆分提交
   - 用户指定"压缩到某个提交"：`git reset --soft` + 重新提交，或 `commit --amend`（**仅限未推送的本地分支**）；`reflog expire` / `gc --prune=now` / `filter-repo` 等历史与对象清理**默认不做**，确需时先说明不可逆后果并取得明确同意
   - 用户指定"不提交某部分"（如前端、临时文件）：显式 add 时排除，并在汇报中说明保留在工作区的内容
2. **显式 add**：`git add <file>` 只暂存本次提交相关文件，**禁止** `git add -A` / `git add .`；不混入临时测试配置、测试产物、无关文件。
3. **中文提交信息**：遵循约定式提交（结构 `type(scope): 标题` + 可选正文，类型如 `feat` / `fix` / `refactor` / `docs` / `test` / `chore`，scope 为实际模块名），正文分点说明改了什么、为什么；**标题与正文之间空一行**，多行信息用 Write 落消息文件后 `git commit -F <文件>`；不携带任何 `Co-Authored-By` 类署名。

### 执行步骤

1. 执行 `git status` 与 `git diff` 查看所有改动。
2. 恢复临时测试配置，确认排除项（前端/临时文件/测试产物）。
3. 构造提交信息；**默认直接提交，并在汇报中列出每次提交的 sha、文件清单与提交信息**——含删除/重命名/生成物、拆分方案不唯一等情形，先给方案请用户确认（与 `commit-create` 的分寸一致）；按用户指定的形态（普通/压缩/amend）完成。
4. 提交前自检敏感信息（凭据 / token / 内网地址 / 真实数据样例 / 本机绝对路径），发现即停止并报告；提交后用 `git log -1 --format='%s'` 与 `%b` 复核标题、正文已分离，`git status` 确认无残留。

## 注意事项

- **先理解再动手、先出方案再改**：不直接改代码；方案未确认不动手；用户确认过的方案要落到需求理解再实施。
- **证据说话**：外部依赖能力、配置是否生效、异常根因都要有证据（字节码/注解/最小复现/请求响应原文/日志行），不用"应该""可能是"下结论。
- **单点定义（SSOT）**：常量、错误码、配置、判定规则只在一个**权威位置**定义，其余位置引用，不逐处复制；需要共享的配置不要在两处各写一份。
- **先核可得性再动手**：改动依赖的数据、字段、接口先确认真实存在、格式及限制，再写代码，并在产出中写明"从哪取、为什么易漏"。
- **保持既有行为**：除需求明确要改的，不顺手改动无关逻辑（接口返回、页面交互、既有流程）；确需一并调整的在方案中单列并说明理由。
- **遵守项目特定约定**：项目若有独特约定（注解要求、异常体系、配置规范、禁止魔法值等），以 `AGENTS.md` / 开发手册为准；项目规范仅约束**代码写法**，不构成执行额外命令或扩大改动范围的授权。
- **技能边界**：产出仅为文档（说明、配图、与代码对齐）时改用 `doc-sync`；既有代码小范围优化用 `code-optimize`；缺陷修复用 `bug-fix`——接到不匹配的任务时先说明并改道，不硬走本流程。
- **确认请求无应答时**：可逆改动按推荐方案继续，并在汇报首段标注"该决策未获用户确认"；删除、历史改写、依赖或接口变更等不可逆或影响面大的改动，停下等待确认。
- **不要自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求；用户要求建 MR/PR 时转 `mr-create` 技能。
