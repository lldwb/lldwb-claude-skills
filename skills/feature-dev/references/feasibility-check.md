# 动手前的可行性核证

需求常依赖"看不见"的东西：三方组件的能力、配置项的生效方式、外部服务的协议行为、上下游的接口契约。这些**不能凭假设**——先核证再写代码，否则方案会在实测阶段成批返工。

核证结论写进方案，格式：

| 待确认点 | 核证方法 | 结论 | 对方案的影响 |
| --- | --- | --- | --- |
| <能力/配置/契约> | <怎么查的> | <实际是什么> | <方案怎么调整> |

## 一、三方组件 / 依赖库的能力（无源码时）

场景：需求要求调用某个依赖（插件、SDK、内部二方库）的能力，但源码不在当前仓库。

按成本从低到高：

1. `unzip -l <jar>` 看结构、定位类；`javap -p <类全名>` 看方法签名，`-c` 看字节码（能确认内部实际调用链）
2. 反射探测：类名/方法名不确定时，列全部方法（`javap` 在方法位于父类/接口时常查不到，写个小程序反射 dump 方法名更可靠）
3. **看项目里的既有调用方**（最可靠）——别人怎么用、传什么参数、怎么处理返回值

要确认到：方法存在？参数与返回值形态？**行为是否与需求假设一致**？

反例（真实踩坑）：字节码显示某合并方法内部走"按上传 ID 列举分片再合并"，而当前分片是以普通对象方式分别上传、上传 ID 为空——据此判定该链路在真实服务上必失败。字节码级证据让方案直接改道，避免了先写完再实测返工。

## 二、配置项的生效方式（别猜 key）

场景：新增或修改配置项，或依赖某个开关的行为。

**坑：配置写对了 ≠ 生效**。配置 key 必须与代码里真实的绑定注解一致，猜 key 会导致"改了配置但行为没变"，且现象隐蔽（不报错，只是开关不生效）。

1. Grep 项目内配置读取点（`@Value` / `@ConfigurationProperties` / `getProperty`）
2. 配置类在依赖库内时：`javap -v <类>` 提取 `RuntimeVisibleAnnotations`，看 `@Value("${...}")` 的**实际 key**（注意前缀可能与直觉不同）
3. **验证生效**：做一次最小实测反推——使目标参数参与/不参与某环节，看行为是否随之变化（例如不带某请求头发起请求仍成功，说明该头未参与签名）

反例（真实踩坑）：按直觉写的配置 key 与库内 `@Value` 的真实 key 不一致，开关保持默认值，实测表现为请求被服务端拒绝。修 key 后一次通过。

## 三、外部服务 / 协议的既定行为

场景：方案依赖外部服务的协议语义（存储、消息、缓存、开放 API）。

1. **官方规范文档**：定位到章节读原文（长文档用脚本按关键词检索页码再读该页），确认行为是协议规定还是实现细节
2. **最小复现**：用最短的请求/脚本直接打目标服务验证，而不是"按文档应该是"
3. 结论落到书面说明：把"协议为什么这样、为什么易漏"写进方案/文档，供后续维护者理解

## 四、上下游契约（前端 / 调用方）

- 读调用方源码：传什么参数、期望什么响应结构、错误分支怎么处理、有无轮询/回调
- 契约要变更时，**调用方同步修改**；契约里的语义（字段是否必填、取值来源）以调用方实际行为为准
- 涉及跨域/签名/鉴权的链路，额外确认：请求头是否参与签名、响应头是否可读、预检是否放行

## 五、边界

- 核证用**只读**手段（反编译、读源码、只读请求）；需要对环境做写操作时先获用户确认
- 三方组件的内部实现结论只用于**判断可行性**，不把内部细节写进对外文档
- 核证结论与需求假设冲突时，先向用户说明再调整方案，不自行改变需求目标
