# feature-dev

需求开发全流程工作流：需求分析 → 方案设计 → 规划文档 → 分层实现 → 验证 → 提交。

## 使用

用户提出新需求、新功能、新接口、新链路，或要求对既有链路做较大改造（跨前后端、涉及外部依赖与第三方组件），并要求"从需求分析做到落地""把方案总结出来再执行""先出方案再改"时自动触发；也可显式要求"用 feature-dev skill 完成这个需求"，或要求"全程交互、逐阶段确认"（走「研究 → 构思 → 计划 → 执行 → 优化 → 评审」六阶段模式）。

**边界**：本技能覆盖从需求到落地的完整开发流程（含方案确认、规划文档、端到端实测闭环）；既有代码的小范围优化（重复代码抽取、性能、结构、可读性）用 `code-optimize`；缺陷定位与修复用 `bug-fix`；产出仅为文档（说明、配图、与代码对齐）的改动用 `doc-sync`。

## 能力

- 全流程：需求分析（含可行性核证）→ 澄清歧义 → 方案设计 → 规划文档 → 分层实现 → 验证 → 收尾提交（步骤与验收见 `SKILL.md`）
- 需求完整性评分：目标明确性 3 / 预期结果 3 / 边界范围 2 / 约束条件 2（满分 10），低于 7 分先补齐关键信息再进入方案设计
- 可选交互式六阶段模式（研究 → 构思 → 计划 → 执行 → 优化 → 评审）：模式标签、阶段门禁、执行后自动优化自检（仅本次改动）、评审阶段派只读子代理独立对账（改造与审查分离）、计划归档、时间戳取真值
- 先理解再动手、先出方案再改，关键决策点交用户确认（人在环）
- 方案设计前先过"要不要写"的阶梯：备选路线的**第 0 项固定为"不做 / 复用既有实现 / 用标准库或既有依赖"**，先证明它不成立再讨论新增（删除优于新增）；主动保留的简化须写明「简化了什么 / 上限在哪 / 如何升级」
- 外部依赖能力、配置生效方式与既有实现的覆盖范围用只读手段核证（反编译、注解提取、最小复现、扫全量监听者与实现者），不凭假设
- 端到端实测取证与分轮迭代：浏览器 MCP（网络请求 + 控制台 + 页面状态）、日志按 trace_id 定位、服务侧最小复现；部署 → 实测 → 证据定位根因 → 修复 → 再测，每轮明确告知用户下一步操作
- 提交：约定式提交、显式 `git add`、不自动 push/merge/PR；按用户要求支持压缩提交/amend/排除前端与临时文件
- 交叉引用：日志排查用 `log-diagnose`、前端报错用 `frontend-error-diagnose`、单测用 `unit-test`、文档同步用 `doc-sync`、提交用 `commit-create`
- 四份参考件在流程里被显式读取（不是可选附件）：核证前读 `references/feasibility-check.md`、实测前读 `references/e2e-verify.md`、出规划文档时用 `references/plan-doc-template.md`（三件套骨架与「何时落盘」判据）、评审阶段用 `references/review-agent.md`（评审子代理提示词模板）
- 提交前后自检：敏感信息扫描（凭据/内网地址/真实数据/本地路径）+ `git log -1 --format='%s'`、`%b` 复核标题与正文已分离

## 文件

- `SKILL.md` — 技能指令（唯一入口）
- `references/feasibility-check.md` — 动手前的可行性核证（三方组件 / 配置绑定 / 协议行为 / 契约 / 既有实现的覆盖范围）
- `references/e2e-verify.md` — 端到端实测与取证（部署节奏 / 浏览器取证 / 日志 / 收尾检查）
- `references/plan-doc-template.md` — 规划文档三件套模板（proposal / design / tasks）与「何时落盘、何时只在对话里出方案」判据（用户指定文档形态 / 路径时从其指定）
- `references/review-agent.md` — 评审阶段只读子代理提示词模板（对照计划与验收标准核对完成度）

## 依赖

- 项目自身的构建与测试工具（按项目实际选择，如 Maven / Gradle / npm，以项目 `AGENTS.md` 为准）
- 浏览器 MCP（端到端实测取证）与日志通道（后端异常定位）
- git（本地提交）
