# bug-fix

Bug 修复的标准工作流：先理解再动手，按「问题现象 → 原因分析 → 修改方案 → 涉及文件」四段式定位根因，修改后编译/测试验证，最后按仓库规范提交 git。

## 使用

用户提出 bug（现象描述 / 报错信息 / trace_id / 复现步骤 / 涉及模块/页面）时自动触发；也可显式要求"用 bug-fix skill 修复这个 bug"。

**边界**：改动仅落在注释层面用 `comment-supplement`；只需定位前端报错、不改代码用 `frontend-error-diagnose`；对外行为不变的结构性改造用 `refactor`；小范围代码优化用 `code-optimize`；新增或改变对外行为用 `feature-dev`。**根因不在本项目代码**（运行环境、第三方依赖、工具链层）时仍走本流程，但改动落在环境侧、不产生 git 提交。实际是**非缺陷的资产维护类任务**（覆盖补全、产物 / 数据同步、批量补齐既有资产）时，按取证与验证的要求推进即可、不套缺陷叙事；同类任务反复出现且无技能覆盖时，向用户提议沉淀为独立技能。

## 能力

- 先读 `AGENTS.md` 与开发规范，按需加载相关章节（勿全文加载）
- 复现驱动定位：后端问题可结合 `log-diagnose` 取日志上下文
- 无法复现的静态缺陷（死代码、注释与实现漂移、规范偏差）用**现状取证**替代复现：全仓引用计数、定义处与调用处对照，并写明"无运行期现象"
- 截图 / 抽样证据的口径：截图是线索不是结论（先核验现象是否仍是当前状态，程序可能仍跑着旧代码）；证据来自抽样时先做同类问题的全量清点，再归类一次性处置——清点按**表述形态**（哪一类句子 / 字段）枚举，不按当前那一处的字面值（按字面值会漏同形态实例，导致用户二次指出）
- 涉及业务数据状态时用 `db-query` 核对（生产只读、只查不改；测试环境写操作须先获用户确认）
- 修根因、最小改动：不做症状屏蔽（加判空 / 吞异常 / 放宽校验），不夹带无关重构
- 验证：按项目实际构建与测试命令执行编译/单测（单模块项目去掉 `-pl <模块> -am`），涉及数据的修复查库对比修复前后数据
- 取证清单：`references/root-cause-checklist.md` 给出复现路径（含截图 / 抽样证据口径）、调用链与依赖排查、环境与工具链故障取证（隔离复现、复合报错拆内层、上游包缺陷判定、受限网络取依赖）、失败分类（本次引入 vs 既有无关）、证据产出与上下文节制（落盘 + 截断 + 写明取数基准）
- 提交：约定式提交、显式 `git add`、标题与正文之间空一行且提交后复核 `%s`/`%b`、不自动 push/merge/PR

## 文件

- `SKILL.md` — 技能指令（唯一入口）
- `references/root-cause-checklist.md` — 缺陷定位与取证清单（按需加载）

## 依赖

- git（提交改动）；项目自身的构建与测试工具（Maven / Gradle / npm / pytest 等，命令以项目 `AGENTS.md` 为准）
- 可选：`db-query`（数据状态核对）、`log-diagnose`（日志拉取）；未安装时改用项目自身的数据库查询能力 / 日志平台
