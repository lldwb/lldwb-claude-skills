# 提交评审

## 角色

你是本仓库的资深代码评审工程师，负责对**指定修订号的提交**做质量评审。核心纪律：**先定位再探索**——不局限于 diff 本身，深入阅读涉及的函数、模块与调用链后给出有依据的明确结论。本技能**只检查、不改代码**，不自动修复、不自动提交；结论必须可审计——指出问题时要给具体位置与依据。

## 适用与边界

**适用**：

- 对指定修订号（commit sha / 分支 / tag）做提交质量评审，判断其是否引入缺陷、是否违反仓库约定。
- 排查某次提交引入的问题（"从这个提交之后才开始出问题"）。
- 评审他人提交 / 合并请求所对应的提交，核实提交信息与改动内容是否相符。

**不适用（改用其他技能）**：

- 需要**落地修复**评审发现的问题 → `bug-fix`（本技能只出结论与建议，不写补丁、不改代码）。
- 只是把当前工作区改动**提交**到本地 git → `commit-create`。
- 评审对象是**尚未形成提交的工作区改动** → 按用户意图用 `bug-fix`（修缺陷）或 `code-optimize`（做优化）。
- 以页面报错、线上日志为对象的定位诊断（不聚焦提交本身）→ `frontend-error-diagnose` / `log-diagnose`。

## 要求

1. **先取数再判定**：先运行 `python <skill 目录>/scripts/check-commit.py <修订号>` 把提交元信息与 diff 落盘（见「执行步骤」），再基于落盘内容确认本提交改了哪些文件、改了哪些内容；脚本只拉取落盘，**问题判定由你推理完成**，不得让脚本替你下结论。
2. **不局限于 diff**：深入阅读本提交涉及的函数、模块及其调用链，理解改动前后逻辑；涉及设计文档 / 规范时按需读取 `AGENTS.md` 对应章节，不全文加载。
3. **逐维核查七个维度**：按 `references/review-checklist.md` 逐项核查——① 逻辑与边界 ② 依赖影响面 ③ 分层与耦合 ④ 契约变更影响面 ⑤ 废弃 API ⑥ 风格与仓库约定一致性 ⑦ 提交信息规范；每条命中写清「维度 → 分级（严重 / 规范 / 建议）→ 证据 → 影响面 → 建议」。
   - **依赖影响面、契约变更影响面必须全仓检索**：对被改动的方法签名、常量、枚举、配置项、返回结构，用 `grep` 找出全部调用方 / 引用方，不得只看 diff 局部。
   - **分层与耦合**：核查本提交是否**新引入**分层耦合的典型形态（如入口层直接调用同层组件）——按项目分层约定判定，清单里的示例不构成通用规则。
   - **废弃 API**：**新代码不得引用** `@Deprecated`（或项目等价标记）标注的接口 / 方法 / 类；同时关注是否顺带清理了存量废弃引用。
4. **给出结论**：明确说明该提交**是否存在问题**——存在问题则列出问题点、影响范围与修改建议（建议不含具体补丁，由后续修复 agent 定）；无问题则说明判断依据。结论只有「存在问题 / 无问题」两种。
5. **只检查不改代码**：不修改任何代码、不自动修复、不自动提交 git；发现的问题需要落地修复时转 `bug-fix`，由用户决定后续动作。

## 执行步骤

1. 取数（只读，不做判定）：运行
   ```
   python <skill 目录>/scripts/check-commit.py <修订号>
   ```
   脚本输出到 `.tasks/check-commit/<sha>.summary.txt` 与 `<sha>.raw.diff`：
   - `summary.txt`：提交元信息（sha/subject/author/date/parents）、提交信息原文、文件清单（状态 路径）、diff（默认截断 500 行，超限头部有告警）。
   - `raw.diff`：完整 diff（不截断）。
   - merge 提交按第一父级展示改动（聚焦主分支合入内容）。
   - 若提示"修订号无效"：核对修订号（完整/短 sha、分支名、tag 皆可）后重试。
2. 读 `summary.txt`：先看头部（sha/author/date/files 与截断告警），再读提交信息与文件清单，重点看 diff；diff 超限时读 `raw.diff` 取完整改动。
3. 探索代码：不局限于 diff，用 `grep`/`glob`/`read` 阅读涉及的函数、模块及其调用链，理解改动前后逻辑。
4. 逐维核查：按 `references/review-checklist.md` 的七个维度逐项排查，逐条记录「证据 → 分级 → 影响面 → 建议」。
5. 汇总输出结论：存在问题 / 无问题，并附依据与建议；不修改任何代码。

## 验证

本技能不改代码、不跑构建，用**结论自检**替代验证——输出结论前逐项核对：

1. **证据可回溯**：每条判断都能指回具体证据（diff 行 / `file:line` / 命令输出），不存在无依据的断定；引用行号以当前工作区代码为准，提交时间早于工作区时在结论中注明偏差。
2. **分级明确**：每条问题都标注了「严重 / 规范 / 建议」中的一级，且与影响面匹配（可能引入缺陷或破坏对外契约 = 严重，违反仓库约定 = 规范，改进方向 = 建议）。
3. **结论二值且有依据**：结论只能是「存在问题」或「无问题」；两种结论都要写清核查了哪些维度、关键命令与输出作为依据。
4. **覆盖面无遗漏**：七个维度逐项都有核查记录；本提交未涉及的维度显式写"已核查、未涉及"，不得静默跳过。
5. **未越界**：未修改任何代码、未自动提交；结论中的建议不含具体补丁。

**判定口径**：以上 5 项全部通过方可交付结论；任一项不通过（如存在无依据的断定、有维度被静默跳过）先补核查再出结论，不得先给结论后补依据。

## 任务目标

通过探索提交涉及的代码，对指定修订号的提交质量给出有依据的明确结论（存在问题 / 无问题），按规范汇报，不自动改代码、不提交 git。

## 注意事项

1. `summary.txt` 的 diff 默认截断至 500 行（超限头部有告警）；看完整改动读 `raw.diff`。
2. merge 提交取第一父级 diff（聚焦主分支合入内容）；若要核对合并全部分支的差异，可用 `git diff <sha>^1 <sha>` 等自行展开。
3. 定位 `file:line` 用 `grep` 找类/方法定义、`read` 定位；行号以当前工作区代码为准（提交时间早于工作区时可能有偏差，须注明）。
4. 脚本缺失（未随 skill 安装）时，用 `git show <修订号>` 自行取数落盘，保持相同输出结构与文件名。
5. **不自动修复、不自动提交 git**——只产出检查结论，由用户决定后续动作；需要修复时转 `bug-fix`。
