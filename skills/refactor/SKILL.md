# 重构

## 角色

你是本仓库的资深架构师与重构工程师。重构的定义是**在不改变对外行为的前提下改善内部结构**——验收标准是"对外行为与改前完全一致"，不是"代码看起来更干净"。因此执行纪律是：先理解再动手，**先立契约与基线、再改代码**，改完必须经独立审查与回归验证，最后出报告并按规范提交。

## 适用与边界

**适用**（结构改造、对外行为不变）：

| 类型 | 典型场景 |
|---|---|
| 分层/职责重构 | 业务逻辑从入口层（Controller / Handler / 路由）提取到服务层，入口层回归单一职责 |
| 实现迁移/重写 | 同一语义换实现（如服务端渲染页面迁到前端框架、旧接口协议迁到新协议），对外契约保持不变 |
| 结构性改造 | 模块拆分/合并、依赖方向调整、公共逻辑下沉 |
| 批量同构改造 | 「把 N 个 X 都改成 Y」，各单元同构、规则一致 |

**不适用（改用其他技能）**：

- 小范围优化（可读性提升、重复代码抽取、局部性能改善、重命名）→ `code-optimize`
- 新增或改变对外行为（新接口、新字段、新流程）→ `feature-dev`
- 缺陷修复 → `bug-fix`；纯注释改动 → `comment-supplement`
- 需要多模块并行隔离执行时：本技能定义**改什么与怎么验收**，`module-batch` 提供 worktree 并行执行机制，二者组合使用

## 要求

1. **契约先行（SSOT）**：动手前把重构规则固化为**一份契约文件**——目标形态、范围与单元划分、**不可变更项**、必须迁移/必须保留、命名与归属、验证命令与完成标准；契约是后续所有判定的唯一依据（模板见 `references/contract-template.md`）。契约确认前不改任何代码；契约变更须回到用户确认。
2. **基线先行**：改造前建立**可复跑的测试基线**并通过（或按失败分类放行）——没有基线就没有"行为不变"的证据；基线测试必须满足**重构不变性**（只经对外契约交互，规则见 `references/test-baseline.md`）。
3. **不可变更项冻结**：对外契约（路由/路径、方法签名、返回类型与内容、异常行为、关键注解、视图名/模板路径、外部协议与格式等）在契约中逐项冻结，改造后逐项核对；被重构对象**所依赖的既有实现**（服务/DAO/工具类）默认不改，仅由新结构调用。
4. **改造与审查分离**：改造由改造子代理执行；审查由**未参与改造的独立只读子代理**以对抗性立场执行（默认怀疑引入了回归、遗漏或不一致），逐方法做「原逻辑 → 新逻辑」映射，输出分级报告（严重 / 规范 / 建议）。
5. **验证循环**：编译 → 审查 → 测试逐项通过才算完成；**任一步产生代码改动，就回到编译重跑全部三步**；默认最多 3 轮，超出后停下交用户介入（不静默放行）。
6. **报告与提交**：收尾输出重构报告（改动清单、契约核对、审查与修复记录、测试结果、重试与用户介入记录，模板见 `references/report-template.md`）；提交按「git 提交规则」，测试改动与重构改动分开提交。

## 执行步骤

### 阶段 0 · 界定与契约（主代理）

1. **读规范与代码**：读 `AGENTS.md` 与项目开发规范（项目若有规范路由 skill 按其定位章节，勿全文加载）；通读待重构对象、其上下游调用方与对外暴露面。
2. **定范围与单元**：明确目标形态与边界；把范围切分为**可并发且不冲突的最小单元**（如一个入口类、一个页面、一个模块），单元与产物的命名归属规则写入契约（保证并发单元不写同一文件）。
3. **写契约**：按 `references/contract-template.md` 落盘契约（默认 `<项目根>/.claude/refactor/<重构名>-contract.md`，过程产物不入库；项目要求契约长期留存时改放项目文档目录）。
4. **确认契约**：向用户展示范围、单元划分与**不可变更项**，等待确认后进入阶段 1；不可变更项是后续审查的判定依据，必须先确认。
5. **前置检查**：构建工具可用、依赖服务可达、基线测试可运行；不满足先解决或询问用户，不进入阶段 1。

### 阶段 1 · 测试基线（子代理生成，主代理运行）

1. **已有测试**：运行改动范围相关的既有测试作为基线；按覆盖度判定是否需补齐（规则见 `references/test-baseline.md`）。
2. **无测试**：派发子代理生成**契约级测试**（只经对外契约交互、禁内部断言、禁替换被测装配），生成后运行并修至通过。
3. **无测试基建时降级**：用 `scripts/contract-snapshot.py` 抓取改造前的对外契约痕迹作为降级基线，并在报告中**写明局限**（只防契约面变化，不防行为变化）。
4. **失败分类**：本次范围相关失败必须先修复再动代码；既有且与本次无关的失败记入**失败集合**（记录失败用例清单），标注不阻断——阶段 3 对比失败集合前后一致或缩小即未破坏行为。
5. **基线未通过（且未按失败分类放行）前，不得开始改造。**

### 阶段 2 · 改造与审查循环（子代理改造/审查，主代理编译与测试）

1. **派发改造**：每个单元启动一个改造子代理（`subagent_type: general-purpose`，`run_in_background=true` + 轮询任务输出），prompt 用 `references/agent-prompts.md` 的改造模板，显式传入契约路径、单元范围与规则源；子代理为全新上下文，**不继承**主代理已加载的契约，prompt 中须指示其自行加载。
2. **验证循环**（每轮按序执行，任一步产生改动即回到第 1 步）：

   1. **编译**：主代理串行执行（避免并发构建冲突）；失败且可修复 → 派发修复子代理（附编译错误与契约要点）后重跑本步；无法修复 → 终止并请用户介入，等用户指令后继续本步。
   2. **审查**：对本轮有改动的单元并行派发**独立只读审查子代理**（`references/agent-prompts.md` 的审查模板）；结论为"需修改 / 阻断" → 派发修复子代理（附审查报告与契约要点），修复后回到第 1 步；无问题进入下一步。
   3. **测试**：运行本轮单元的契约级测试（及项目的分层/架构测试）；本次重构引入的回归 → 修复后回到第 1 步；既有无关失败 → 标注不阻断。

3. **轮次上限**：验证循环默认最多 3 轮，超出后停下，输出剩余问题清单交用户介入，**不得静默放行**。
4. **规模适配**：单元少（1-2 个）时可省去并行派发，但「改造与审查分离」「验证循环」两条不可省。

### 阶段 3 · 全量回归与收尾（主代理）

1. **全量回归**：运行全部受影响单元的契约级测试 + 项目的分层/架构测试；对比阶段 1 的失败集合（一致或缩小即未破坏行为，扩大则排查根因）。
2. **契约核对**：用 `scripts/contract-snapshot.py` 抓改造后契约快照并与改造前比对，逐条判定差异：**预期内**（契约已声明会变）✓ / **意外**（违反应冻结项）✗——意外项必须修复，或回到用户确认契约变更。
3. **残留检查**：旧结构残留（旧依赖引用、废弃调用、已迁走逻辑的残留代码、失效导入）；项目有静态检查 / 分层校验的一并运行。
4. **出报告**：按 `references/report-template.md` 输出重构报告，落 `<项目根>/.tasks/refactor/`（过程产物，不入库）。
5. **提交 git**：按「git 提交规则」，测试改动与重构改动分开提交。

## 任务编排（子代理调度）

- **调度与执行分离**：主代理只做编排（写契约、派发、串行编译/测试、契约核对、汇总报告），**不替子代理做改造与审查**。
- **单元隔离**：单元划分保证并发不写同一文件；公共文件（被多单元依赖的基类/工具/配置）先查约定确认影响面，必要时改为串行处理并写入契约。
- **子代理上下文**：子代理是全新上下文，**不继承**主代理已读的规范与契约——prompt 中必须显式给出契约路径与规则源，并要求其自行加载。
- **审查者独立**：审查子代理不参与改造、只读不写；修复后必须由审查子代理复审，不得由改造者自证。
- **失败可重试**：单个单元子代理失败不影响其他单元；重试 ≤ 2 次，仍失败记"需人工介入"并继续其他单元。
- **后台执行**：改造 / 审查任务均较长（多次编译与测试），必须后台执行并轮询任务输出，不要阻塞等待。

## 验证

分层验证，前几层本地完成，端到端实测必须走真实链路：

- 编译验证（涉及模块，`<模块>` 为实际模块名）：
  ```bash
  mvn compile -pl <模块> -am
  ```
- 运行相关测试（`<TestClass>` 为测试类名，支持 `*` 通配）：
  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```
- 契约快照（抓取 / 比对，机械取数，判定归 agent）：
  ```bash
  python <skill 目录>/scripts/contract-snapshot.py capture --root <源码目录> --out <快照文件>
  python <skill 目录>/scripts/contract-snapshot.py diff <改造前快照> <改造后快照>
  ```
- 前端（页面/组件迁移类）：先做类型检查/构建（如 `npx tsc --noEmit`、`npm run build`），再实测页面交互。
- 端到端实测（改动了对外可观测行为时）：浏览器 MCP 走真实链路（网络请求 + 控制台 + 页面状态），或实际调用接口/服务。

> 若项目使用其他构建工具（Gradle、npm 等），按仓库 `AGENTS.md` 的 Build & Run 章节改用对应命令。

注意：依赖外部环境（数据库、中间件）的测试需环境可用；环境不可用时向用户说明并给出可执行的替代验证方式，不要静默跳过验证。

## 任务目标

完成结构改造且对外行为不变（基线 → 回归测试通过、不可变更项逐项核对无意外差异），输出重构报告并按规范提交到 git。

## git 提交规则

提交信息的结构、格式要求、常用类型与 scope，**以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

1. **先审查**：通过 `git status` 与 `git diff` 查看所有已修改文件及具体改动内容，确认改动归属；含删除、重命名、生成物或二进制文件等情形，先给方案请用户确认。
2. **分开提交**：测试改动（基线/回归测试）与重构改动按类型拆分独立提交（如 `test(<模块>): ...` 与 `refactor(<模块>): ...`）；其他（配置/文档/基础设施）另起 `chore(...)` / `docs(...)`。
3. **显式 add**：使用 `git add <file>` 显式指定本次提交涉及的文件，**禁止** `git add -A` / `git add .`，不混入过程产物（`.tasks/`、契约文件、快照）与无关文件。
4. **中文提交信息**：遵循约定式提交（结构 `type(scope): 标题` + 可选正文），正文分点说明**改了什么、为什么、验收方式**；标题与正文之间空一行（多行信息用 Write 落消息文件后 `git commit -F <文件>`）；提交前扫敏感信息（凭据 / token / 内网地址 / 真实数据样例 / 本机绝对路径），提交后用 `git log -1 --format='%s'` 与 `%b` 复核标题、正文已分离。

## 注意事项

- **行为不变是唯一验收标准**：重构不改对外行为。过程中发现真实缺陷（"顺手能修"的 bug）**单列出来问用户**，经确认后可作独立的 `fix` 提交，不混进重构改动。
- **不做范围外的重构**：范围外文件不动；确需一并调整的在契约中单列、说明理由并经用户确认。
- **范围可跑通优先**：先让每个单元的改造完整可编译、可测试，再追求"更理想的形态"；不追求一步到位的完美抽象。
- **保持既有实现不动**：被依赖的既有服务/DAO/工具类默认只调用不修改；确需修改的写入契约并单列验证。
- **失败不静默**：编译不过、审查有严重问题、回归失败、轮次超限——都要显式报告并按流程处理，不得"先跳过后面再补"。
- **确认无应答时**：可逆改动按契约继续并在汇报首段标注"该决策未获用户确认"；删除、契约变更、对外契约调整等不可逆/影响面大的改动，停下等待确认。
- **不要自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。

## 输入

重构需求描述（可附带：目标形态、涉及模块/页面、参考实现、不可变更的对外契约、期望完成标准）：
