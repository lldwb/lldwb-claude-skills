# 结论输出模板（前端报错诊断）

> 供 agent 按需加载的参考件：**输出诊断结论前读**。本文件给出可直接照抄的结论模板、逐段填写要求与未复现时的写法；产出核验口径（证据可审计、复现或降级声明、证据落盘、方案可执行、未改代码）见 `SKILL.md` 的「验证」节。

## 一、模板（照抄，按实际填充）

```text
现象：
1. <用户可见的表现 + 报错文案>

证据：
1. console：<报错类型与完整 stack，指向 文件:行>
2. 网络：<失败请求 method / URL / 状态码 / 响应体摘要>
3. 其他：<截图 / DOM / 运行时状态 / 环境与版本；给出落盘文件路径>

根因：
1. <直接原因 → 根本原因，说明证据如何支撑该结论>

修复方案：
1. <推荐方案：改哪个文件、怎么改、为什么>
2. <备选方案（若有）及其影响范围>

影响范围与回归点：
1. <受影响的功能 / 页面 / 用户范围>
2. <改完需要回归验证的点>
```

## 二、逐段填写要求

1. **现象**：写用户可见的表现（白屏、报错弹窗、某个功能无响应）+ 报错原文；多条现象按出现顺序编号，说明彼此是否连锁触发。
2. **证据**：只列**实际采到**的记录，逐条编号；console 段必须含报错类型与完整 stack，并给出还原后的 `文件:行`；网络段至少含失败请求的 method / URL / 状态码与响应体摘要；截图、控制台与网络导出给出**落盘文件路径**便于复核。采集不全时在段末写明缺哪一项及原因。
3. **根因**：一句话给直接原因，再给根本原因，并说明**哪几条证据支撑**该结论（引用证据编号）；不得只给结论不给支撑。
4. **修复方案**：推荐方案必须落到「改哪个文件、怎么改、为什么」；有备选方案时列出并说明影响范围与代价差异；指向后端或数据的，写明需转交的技能（`log-diagnose` / `db-query`）与该侧需核对的点。
5. **影响范围与回归点**：写受影响的功能 / 页面 / 用户范围（是否全量、是否仅特定角色或数据），以及改完必须回归验证的点。

## 三、未复现时的写法

在「现象」段之后紧跟一行**复现状态声明**，写明取了 `SKILL.md`「无法复现时的降级」的哪一档与原因，再按档位收尾：

- 第 1 档（换环境 / 账号 / 数据）：写明已试过的组合与结果，给出下一步可试的组合。
- 第 2 档（无浏览器 MCP）：写明索要的取证材料是否已拿到（console 原文与 stack、失败请求完整响应），已拿到的把原文贴进「证据」段。
- 第 3 档（仍无法复现）：结论只给**可能性排序**——每条可能性标注依据强度（有证据支撑 / 仅与现象相符）与下一步取证建议，**不给确定性根因**；「修复方案」段相应改为「按各可能性的验证路径」，不得直接给改动建议。

## 四、常见不合格写法（自检时逐条排除）

- 结论里出现"可能是""大概是"而无任何证据指向 → 补证据或降级为可能性排序。
- 只贴报错文案就给出根因 → 回到「证据」段补齐 console stack 与失败请求。
- 截图 / 导出只在会话里口述、未落盘或未给路径 → 落盘并补路径。
- 未复现却给出确定性根因与直接改动建议 → 按第三节第 3 档重写。
- 把「改哪个文件、怎么改」写成泛泛的方向（如"加上判空"）而未指向具体位置 → 补 `文件:行` 与改法。
