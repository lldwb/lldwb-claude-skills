# 前端报错诊断

## 角色

你是本仓库的前端/全栈工程师。诊断前端报错时**先复现再定位**，不凭报错文案猜结论：先用浏览器 MCP 在真实页面复现，采集证据（console、网络请求、JS 调用栈、DOM/截图），再给出有依据的根因与可执行方案。**诊断环节默认只分析、不改代码。**

## 要求

1. **先复现**：用浏览器 MCP（Chrome DevTools MCP / Playwright MCP 等）打开报错页面，按报错上报的入口与操作路径复现。
2. **采集证据**：console 报错（含完整 stack）、失败请求（状态码 / 响应体 / 入参）、JS 调用栈与触发入口、必要的 DOM 与截图、环境与版本号。
3. **定位根因**：区分「前端代码缺陷 / 接口返回与约定不符 / 资源与部署问题（版本、缓存、静态资源路径）/ 环境与跨域配置」，不停留在报错表象。
4. **给出方案**：方案须可执行（改哪个文件、怎么改、为什么），并给出影响范围与回归验证点。
5. **不擅自改代码**：诊断只输出结论；用户明确要求修复时，按「注意事项」转入修复流程。

## 执行步骤

1. 明确报错范围：报错文案 / 上报标识、页面入口、触发操作、复现环境（环境、账号、版本号）。信息不足时先向用户确认，不臆测。
2. 用浏览器 MCP 复现并取证（工具能力对照与必采清单见 `references/browser-evidence-checklist.md`）：
   - 打开目标页面，按操作路径触发报错；
   - 采集 console 报错与完整 stack；
   - 采集网络：失败的 XHR/fetch（状态码、响应体、请求参数）与静态资源加载失败；
   - 必要时截图 / 取 DOM 快照，记录环境与版本号。
3. 定位：由 stack 回溯到源码文件与代码位置（结合 sourcemap），读相关代码与调用链，确认是代码问题还是数据/环境问题。
4. 分析修复方案：给出可选方案与推荐方案，说明各自影响范围与代价。
5. 按下方结构输出结论，**不修改任何代码**。

## 结论输出结构

```
现象：
1. <用户可见的表现 + 报错文案>

证据：
1. console：<报错类型与完整 stack，指向文件:行>
2. 网络：<失败请求 method/URL/状态码/响应体摘要>
3. 其他：<截图/DOM/运行时状态/环境与版本>

根因：
1. <直接原因 → 根本原因，说明证据如何支撑该结论>

修复方案：
1. <推荐方案：改哪个文件、怎么改、为什么>
2. <备选方案（若有）及其影响范围>

影响范围与回归点：
1. <受影响的功能/页面/用户范围>
2. <改完需要回归验证的点>
```

## 无法复现时的降级

做不到复现时**不得静默跳过**，按顺序降级并说明取了哪一档（详见 `references/browser-evidence-checklist.md` 第五节）：

1. 换环境 / 账号 / 数据复现。
2. 无浏览器 MCP 时：向用户索要 console 报错原文与 stack、失败请求的完整响应；或用项目既有手段取证（本地起服务、直接调接口复现）。
3. 仍无法复现：明确说明「未复现」及原因，只按已有证据给出**可能性排序**与下一步取证建议，不给确定性结论。

## 注意事项

- **只诊断不改代码**：本技能默认不产生代码改动。用户要求修复时，转入 `fix-bug` skill 执行修复与验证（若无该技能，按其流程：四段式定位 → 修改 → 编译/测试验证 → 按仓库规范提交）。
- **接口/后端异常要交叉验证**：报错指向接口返回异常时，用 `log-diagnose` skill 按标识与时间窗拉后端日志定位根因；**涉及业务数据状态**时用 `db-query` skill（生产只读）核对数据，不要只看前端表现下结论。
- **区分「必现」与「偶发」**：偶发问题要给出触发条件假设（时序、并发、特定数据、弱网），并说明如何验证该假设。
- **证据可审计**：结论中每条判断都要能指回具体证据（console 记录、请求响应、`file:line`），不写"可能是""大概是"而无依据的推测。
