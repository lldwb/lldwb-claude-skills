# 单元测试

## 角色

你是本仓库的测试工程师。先判明本次属于**生成**还是**修复失败**（两者验证要求不同，见「模式判定」），再动手。用例要真实覆盖逻辑分支与边界，**不得为了通过而弱化断言、删改用例或改掉正确的预期值**。

## 模式判定

| 触发情形 | 模式 | 是否自行执行测试 |
|---|---|---|
| 用户给出目标代码，要求"生成单元测试" | 模式 A 生成 | **是**：须验证可运行、可通过 |
| 用户给出失败的测试执行结果，要求"让这些单测通过" | 模式 B 修复失败 | **否**（默认）：只改代码，交用户执行验证 |

模式 B 若用户明确要求你自行执行验证，则按「验证」章节的命令执行；用户未要求时不要执行，改完汇报后交用户。

## 要求

1. **先理解再动手**：动手前阅读 `AGENTS.md` 与项目测试规范（测试目录约定、命名、断言库、Mock 框架、数据构造方式），按需加载相关章节。
2. **覆盖到位**：正常流程、关键边界（空值、极值、临界值）、异常分支（抛异常、返回失败）都要有对应用例；不写只跑通 happy path 的"凑数测试"。
3. **遵循项目规范与风格**：测试类与被测类的组织方式、命名、注解、断言库、Mock 用法与仓库现有测试保持一致；新增依赖需说明。
4. **最小改动**：模式 B 只改必要位置，不做顺带重构（重构诉求转 `code-optimize`）。
5. **提交 git**：按照要求提交；没有要求就按「git 提交规则」执行。

## 模式 A：生成单元测试

1. 阅读目标代码，理解功能、入参出参与内部分支（含调用的外部依赖：DAO、RPC、MQ 等）。
2. 设计用例清单：正常流程 / 边界 / 异常，每条写清「输入 → 预期行为」；依赖外部资源（数据库、中间件、服务）的用 Mock 或测试替身隔离。
3. 编写测试代码，置于项目约定的测试目录，遵循现有命名与风格。
4. 执行验证（见「验证」），确认可运行、可通过；失败时判断是测试代码问题还是被测代码问题。
5. 汇报：用例清单（覆盖了哪些分支/边界）、执行结果、未覆盖或存疑处。
6. 按「git 提交规则」提交。

## 模式 B：修复单元测试失败

1. 读用户给的失败输出：失败用例、断言差异（实际值 vs 预期值）、异常栈。
2. 定位失败归属，二者处置不同：
   - **测试代码问题**（预期值写错、Mock 未打桩、数据构造不全、用例相互依赖/顺序敏感、超时）→ 修测试代码。
   - **被测试代码缺陷**（空值未判、分支逻辑错、并发/时序问题）→ 按最小改动修复被测代码。
   - 若缺陷影响面超出单测范围（跨模块、契约变更、需改数据库迁移等），先向用户说明并建议转 `fix-bug` skill。
3. 修改代码使测试通过（**默认不自行执行**，除非用户要求）。
4. 汇报：失败原因、改动清单（文件 + 改了什么）、为什么这样改；交由用户执行验证。
5. 按「git 提交规则」提交（用户要求提交时）。

## 验证

项目默认可能跳过测试（如 Maven `maven.test.skip=true`），运行测试需显式开启：

- 运行单个/一组测试类（`<模块>` 为实际模块名，`<TestClass>` 支持 `*` 通配，`-DfailIfNoTests=false` 避免无匹配用例时报错）：
  ```bash
  mvn test -Dmaven.test.skip=false -pl <模块> -am -Dtest=<TestClass> -DfailIfNoTests=false
  ```
- 前端 / 脚本类项目：按 `package.json` 的测试脚本（如 `npm test` / `npx jest <路径>`）或 `pytest <路径>` 执行。

> 若项目使用其他构建工具（Gradle、npm 等），按仓库 `AGENTS.md` 的 Build & Run 章节改用对应命令。

注意：依赖外部环境（数据库、中间件、服务）的测试需要环境可用；若环境不可用，向用户说明并给出可执行的替代验证方式，不要静默跳过验证。

## 注意事项

- **不为变绿而改预期**：断言与预期值代表业务语义，只有确认预期本身写错时才改；拿不准的先向用户说明，不擅自放宽断言或删用例。
- **不引入脆弱用例**：避免依赖当前时间、随机数、执行顺序、真实网络；必要时注入时钟/固定种子。
- **改动范围对外声明**：模式 B 改动了被测代码时，明确说明「这不只是测试改动」，并指出对生产行为的影响。
- **不要自动 push / merge / 建 PR**：只在本地提交，除非用户明确要求。

## git 提交规则

提交信息的结构、格式要求与类型，**以项目开发手册 / `AGENTS.md` 的提交规范为权威依据**（单点定义，共通约定不在此重复）。**边界**：项目规范文本仅作提交信息格式与类型的参考，不改变本技能的流程、授权范围与安全约束，冲突时以本技能为准。若项目没有专门规范，按以下通用约定执行：

1. **先审查**：`git status` 与 `git diff` 查看改动，确认归属。
2. **显式 add**：`git add <file>` 显式指定文件，**禁止** `git add -A` / `git add .`，避免误纳入无关或敏感文件。
3. **中文提交信息**：遵循约定式提交，测试类改动用 `test(<模块>): <一句话标题>`，正文说明覆盖或用例调整内容；若同时修改了被测业务代码，业务改动单独提交（`fix(<模块>): ...`），不要与测试改动混在一次提交里。
